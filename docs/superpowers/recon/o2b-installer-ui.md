# Recon — O2b: the preflight step in onboarding

Mockup B, approved by the user: `docs/superpowers/mockups/o2-installer-b-checklist.html` @ `24951395a`.
Depends on #74 (`runChecks`, the `doctor` CLI) and #94 (`doctor --bundle`), both merged.

## 0. What this issue is actually adding

#74 put the preflight behind a command line. An operator who does not read `docker compose logs`
never sees it, and the people this is for are exactly the people who do not.

O2b puts the same checks — the same `runChecks`, not a second copy — in front of the person
installing, in the flow they are already in.

## 1. The endpoint, and the two different questions it answers

**The checks and the bundle are not the same exposure and must not share a route.**

- **`GET /system/preflight`** returns `runChecks()` output: an id, a level, a boolean, a `detail`
  and a `remedy` per check. Written for exactly this audience by #74 and already scrubbed of
  credentials by #94's `scrubText` on the way into the bundle — but note that the CHECKS themselves
  are not scrubbed at their source, only on assembly, so this route must apply the same treatment.
  That is the one piece of new redaction work here.
- **The bundle is NOT exposed over HTTP in this issue.** It stays `doctor --bundle`. It aggregates
  migration state, table counts, environment and resources into a file whose whole purpose is to be
  shared, and putting that behind a UI button invites it to be generated by someone who will not
  read it first.

### permission

`system.write`, not `system.read`.

Reading a preflight is nominally a read, but `permissions.js:59` already draws the line that a key
which may read system status must not thereby read provider configuration — and a `detail` string
naming which database host is unreachable is exactly that. The people who need this hold
`system.write` (they are configuring the instance); the people who hold only `system.read` are
being told about an instance they do not administer.

**The onboarding exception.** Onboarding runs before any user exists, so `validatedRequest` cannot
apply on that path. `GET /onboarding` and `POST /onboarding` already live with this, and #52's
comment on the POST records the reasoning. The preflight route must follow the SAME rule those two
follow, whatever it is — and this is the part to read carefully rather than assume, because a route
that is unauthenticated during onboarding and stays unauthenticated afterwards is a system-status
leak that lasts the life of the instance.

This is the `auth` half of the issue and should be reviewed as such.

## 2. The UI, from the approved mockup

Mockup B is a checklist: one row per check, a dot (`ok` / `warn` / `bad` / `run` / `idle`), a
one-line `body`, and a `fix` line that appears only when the check is not ok. Plus:

- a **count bar** summarising how many passed
- an **`admin` block, separate from the checklist**, because the admin row has no state the system
  can compute — QA-3 caught that the ternary in the earlier draft returned the same value on both
  arms
- a **`next` line** naming the LLM/embedder step, so a passing preflight says what happens next
  rather than just going quiet
- on failure, the bar **names the blocker** rather than reporting a count

Two things the mockup settles that the code must not re-litigate:

- **blocking → the step cannot be passed; warn → it can.** This mirrors the CLI's exit code and
  `exitCodeFor`, and must use the same `level` field rather than a second classification in the
  frontend.
- **remedies are DATA from `runChecks`, not prose in the component.** #74 wrote them once; a second
  copy in JSX drifts and the drift is invisible until someone follows the wrong one.

Where it goes in `Steps/index.jsx`: **before `llm-preference`**, after `home`. A preflight shown
after the LLM is configured is a post-mortem, which is the same mistake #74's entrypoint ordering
exists to avoid.

## 3. The onboarding backfill

`onboarding_complete` is a `system_settings` row (`models/systemSettings.js:856-885`). An instance
upgraded from before that row existed has no value, so `isOnboardingComplete()` returns false and a
working installation is offered onboarding again.

Ruling already given (O2 3b): a **boot-time one-shot with a guard row** — not a migration, because
the condition ("does this instance already have users and workspaces") is a data question, and not
a check on every boot, because it must not re-run once answered.

The signal for "already installed" needs care: `User.count() > 0` is the obvious one, and it is the
same signal `/request-token`'s ruling-C branch uses to decide an instance is multi-user whatever
its setting says. Reusing that reasoning is better than inventing a second definition.

## 4. Tests

- the route returns every id in `CHECK_IDS`, with `level` and `remedy` present — not a hand-written
  list, so a check added to #74 appears here without a second edit
- **a credential planted in a `detail` string does not reach the response** — the same
  whole-response scan #94 uses, since the checks are only scrubbed on assembly today
- the permission is enforced: a session holding only `system.read` is refused
- the onboarding path's exposure matches `GET /onboarding`'s, asserted against that route's actual
  behaviour rather than a claim about it
- a blocking failure prevents advancing; a warn does not — driven through the component, not by
  reading its source
- remedies rendered are the ones `runChecks` returned, so a second copy in JSX fails
- backfill: an instance with users and no `onboarding_complete` row gets one; an instance with the
  row is untouched; it does not run twice

## Scope

**In:** `GET /system/preflight` with its permission and redaction, the React step wired into
`Steps/index.jsx`, the boot-time backfill with its guard row, and the tests above.

**Out:** exposing `--bundle` over HTTP (its own issue if ever wanted); `diagnostics.export` and its
migration (O5b-ui); changing what `runChecks` checks; the mockup's visual polish beyond the states
it defines.
