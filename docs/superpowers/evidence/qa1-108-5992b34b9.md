## N7 — the password does not reach the DOM or storage

| # | mutation | result | red |

N7a and N7b are real kills: the assertion reads `document.body.innerHTML`, every `input.value`, and both storages as raw text, so it catches a leak wherever it appears rather than where someone thought to look.

N7c survives because the fixture never puts a password in the GET response — `smtp_password` appears in neither `index.test.jsx` nor `models/mailer.js`. Recorded as NIT-2 below.

The `a stored password is never sent back to the page` test asserts `field.value === ""` with `hasPassword: true`, so the placeholder-instead-of-secret property is pinned.

## NIT-1 — N8 does not pin the guard on the real route

`src/main.jsx:200` mounts `<AdminRoute Component={GeneralMailer} />`. Changing it to `<ManagerRoute .../>` leaves the suite **24/24**.

`adminRoute.test.jsx` renders its own `Secret` component under each guard by hand, so it proves `AdminRoute` refuses a manager and `ManagerRoute` would not — a true and useful statement about the guards. It says nothing about which guard the mailer route actually uses, which is the property the test's own header claims ("the mailer page is behind AdminRoute"). Swapping the guard in `main.jsx` ships a page a manager can open and every call 403s from — exactly the failure the file was written to prevent.

The harness itself is sound: `multiUserMode: true` is load-bearing (the single-user test proves it), the loader wait is real, and the positive control (`an admin IS shown the page`) rules out a guard that refuses everyone.

Fix: assert the mounted route rather than re-mounting by hand — import the route config from `main.jsx` and check the mailer entry's element type is `AdminRoute`, or render the real `/settings/mailer` path through the app router with a manager and assert the page is absent.

## NIT-2 — the GET fixture never carries a secret

`index.test.jsx` never sets `smtp_password` on the settings response, so N7c (page hydrates its password state from the server payload) survives. One line in the existing "a stored password is never sent back to the page" test closes it:

```js
mockFetch({ settings: settingsResponse({ hasPassword: true, smtp_password: PASSWORD }) });
// …then, alongside the existing assertions:
expect(document.body.innerHTML).not.toContain(PASSWORD);
```

That makes the page's `...stored` spread safe against a server that starts returning more than it does today, which is the same defence-against-future-callers argument #49 F1 was accepted on.
