## My deny-only-group finding: withdrawn as a blocker, kept as a residual

My pre-check argued the `groupPerms.size === 0` early return (`:132`) lets any actor pull a
user out of a group that carries only `document_acl` denies, since a deny-only group has no
`principal_role_grants` row. The mechanism is real — `documentFilter:91-99` reads deny rows for
every group the actor belongs to, and `permissionIdsForGroup` cannot see them.

**But it is not reachable today, and I was wrong to weigh it as a blocker.** Measured:
`grantDocumentAcl` has no caller outside tests (`documentFilter.test.js:190`,
`pinnedContextAcl.test.js` ×5), and the only seeded `document_acl` rows are
`principal_type: 'workspace'` (`migration.sql:387-392`). Nothing in the product writes a
group-principal deny row, so there is no deny-only group for the early return to mishandle. The
ruling PMO took — the guard measures what the group carries, and refusing an empty group would
block ordinary directory sync — is right for every group that exists.

Recording it because the first caller that writes a group deny row reintroduces it silently:
that code will be reviewed as "a deny feature", and the membership guard is in another file.
