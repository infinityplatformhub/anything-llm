## My conditions, each measured

### One implementation, stamp inside the transaction — CONFIRMED

Both delete routes run `offboardUser` → `revokeCredentialsFor` → `tx.users.delete` inside a
single `prisma.$transaction`. `revokeCredentialsFor` is exported from `models/user.js`
rather than reimplemented, so the `revokedAt` stamp has exactly one implementation. This is
the self-found regression Dev2 reported and the fix is the right one — the alternative
(routes doing their own `updateMany`) is the two-places-know-the-same-thing shape I have
rejected three times this cycle.

I verified the stamp behaviourally rather than by reading, driving the real admin route:

```
unmutated: status 200 | key row present: true | revokedAt set: true
under M2:  status 200 | key row present: true | revokedAt set: false
```

Ordering is correct at all three sites: offboard **before** delete, so a refusal leaves the
account whole. **M3** (reorder the v1 route to delete first) — see NIT-1.

### 403 + JSON body + server-side attribution — CONFIRMED at the API route

`endpoints/api/admin/index.js` catches `AuthorizationContractError`, logs a line naming
`role.revoke`, and answers `403 {"error":"Forbidden."}`. That is exactly ruling (iii):
generic body, action recorded server-side, and it fixes the `res.json()` throw QA-3 found
because the body is valid JSON. The fixture asserts `status === 403`, `body` deep-equals
`{error:"Forbidden."}`, and that a logged line matches `/role\.revoke/` — not
`not.toBe(200)`, which any crash satisfies.

### The admin route's 200 + `success:false` — correct as asserted

The fixture records a measurement that contradicts my own expectation and Dev2 was right to
assert what happens rather than what I predicted: `validCanModify` runs before the offboard
and calls `canAssignLegacyRole`, which the weak actor also fails, so the request is refused
earlier with the route's existing `200 {success:false}` shape. The 403 path is exercised at
the API route, which has no `validCanModify` ahead of it. Asserting the real behaviour and
naming why is the right call.

The refusal fixture is well built and I want to name three things it does that most do not:
it **constructs** the weak role (no seeded role holds `user.manage` without `role.revoke` —
my measurement, reconfirmed here), it **proves it built what it claims** by reading back the
role's permissions and asserting `role.revoke` is absent, and it asserts the victim actually
holds a grant so the guard is genuinely reached. Without the third, a victim holding only an
ACL passes the test without ever entering `revokeGrant`.

Atomicity is asserted in full — orphan count unchanged **and the user row still present**.

## NIT-1 (non-blocking) — two mutants survive, and both matter

I did not report these as "survived" without measuring what they do.

**M2 — drop `revokeCredentialsFor` from the admin route: 11/11 green.** The probe above
shows what it costs: `revokedAt` stays null on a deleted user's key. The row is orphaned
either way (no FK), so the reader still refuses it — this is the audit record, not the
enforcement, exactly as #136 settled. But it is the record of *when* the credential
stopped, it cannot be reconstructed once the user row is gone, and **no fixture asserts
it**. The two occurrences of `revokedAt` in the suite are both `revokedAt: null` inside a
mock `apiKeyContext`, not assertions.

This is the same regression Dev2 found and fixed. It is currently protected by nothing but
his having noticed. One assertion — after a route delete, the victim's `api_keys` row has a
non-null `revokedAt` — closes it.

**M3 — reorder the v1 route to delete before offboarding: 11/11 green.** Ordering is the
property that makes the behaviour change safe (a refusal must leave the account whole), and
the comments at both sites say so. Under this mutant a refusal deletes the user and *then*
fails — the exact orphan state the issue closes, arrived at from the other direction. The
refusal fixture does not catch it because the transaction rolls the delete back; what the
mutant actually breaks is the guarantee under a *non-transactional* future edit. Lower
value than M2, and I would not block on it, but a comment saying the ordering is
load-bearing-but-unpinned is honest.

Neither blocks: the code is correct at this SHA and both properties are real. What is
missing is the assertion that keeps them correct.
