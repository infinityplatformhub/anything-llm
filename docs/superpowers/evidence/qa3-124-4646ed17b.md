## Why (b) survives — mechanism, run not read

With no `aria-label`, the button's accessible name is its text content, which is the
pre-fix behaviour. Instrumented run (log added to the test, source mutated, both reverted
after):

```
MECH firstName aria-label = null | text = "gpt-4o-mini"
MECH after model resolves, name-matcher finds: 0
```

Two independent reasons, one per test:

- **Test 1** (`the button is reachable by an accessible name…`) passes inside the
  **fallback window**. Before the async model name resolves, `modelName` is `""` and the
  visible text is `t("chat_window.select_model")` — so the name matcher `/select_model|select model/i`
  matches the *visible text*, not any label. `waitFor` succeeds on the first tick and
  never looks again. Adding one `waitFor(getByText(/gpt-4o-mini/))` before the same query
  drops the match count to **0** — proving the assertion is satisfied only by the
  transient pre-load state. This is precisely the timing failure the header comment says
  was already found and fixed in test 2, still live in test 1.
- **Test 2** (`the accessible name does NOT change…`) reads
  `.getAttribute("aria-label")` on both renders. With the attribute gone both sides are
  `null`, and `expect(secondName).toBe(firstName)` is `null === null`. The test asserts
  the *attribute* is stable rather than the *accessible name*; absence is perfectly
  stable. A control with no name at all passes the constancy test.
- **Test 4** (no model set) is the fallback path by construction, so the visible text is
  the key and it matches with or without the label.

Test 3 (visible text still shows the model) is unaffected by the label and correctly
stays green — that one is honest.

So the suite's stated RED claim in its own header —
*"RED before the fix: `getByRole("button", {name: /select model/i})` finds nothing,
because the name is `gpt-4o-mini`"* — is **false as written**: on the pre-fix component
that query finds the button during the fallback window. The suite never had a RED it
could not reach without the fix.

## Timing claim PMO asked me to confirm

**Not satisfied for test 1 or test 4.** Only test 2 reads after the model name is on
screen (`waitFor(getByText(/gpt-4o-mini/))` then read), which is why (a) and (c) die.
Tests 1 and 4 read inside the fallback window, which is why (b) lives.

## `getByLabelText` framing

Not applicable as asked — the suite uses `getByRole(..., {name})`, not `getByLabelText`.
The failure output does read as an a11y report: mutant (c) prints the full DOM with
`aria-label="Workspace"` visible on the button, so a reader sees the wrong name rather
than a harness error. That property is fine; it is the coverage that is missing.

## What would fix it

In tests 1 and 4, wait for the resolved state before querying (test 1: `await waitFor(getByText(/gpt-4o-mini/))`
first, then `getByRole`), and in test 2 compare the computed accessible name (or assert
the attribute is a non-empty string on both sides) rather than an attribute that is
allowed to be `null` twice. Re-run mutant (b): it must go red.
