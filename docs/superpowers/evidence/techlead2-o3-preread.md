## 48 vs 49 — **`directory_sync_checkpoints`** และมันไม่ใช่ของหาย

ผม diff schema กับฐานจริงทั้งชุด:

```
models ที่ประกาศ @default(autoincrement()) :  49
sequences ใน pg_class (public)              :  48
sequences ที่ owned by a column             :  48
ประกาศแล้วไม่มี sequence                     :  ['directory_sync_checkpoints']
มี sequence แต่ไม่ได้ประกาศ                   :  []
```

**สาเหตุ**: migration `20260902130000_directory_sync_checkpoint` สร้างคอลัมน์เป็น
`BIGINT GENERATED BY DEFAULT AS IDENTITY` ไม่ใช่ `SERIAL` — คอมเมนต์ในไฟล์เขียนเหตุผลไว้เอง
(*"IDENTITY, not `serial`: the sequence belongs to the column's lifecycle"*) ·
Prisma แทน identity ด้วย `@default(autoincrement())` ในสคีมา ทั้งที่ postgres จัดเก็บคนละแบบ

**ไม่มีอะไรหาย** · ผมทดสอบทั้งสองรูปแบบบนฐานเปล่า:

```
CREATE TABLE ident_t  (id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY)
CREATE TABLE serial_t (id SERIAL PRIMARY KEY)
-> pg_class relkind='S':  ident_t_id_seq   serial_t_id_seq      <- ทั้งคู่มี sequence
-> pg_get_serial_sequence('ident_t','id') = tl2probe.ident_t_id_seq   <- ทั้งคู่ resolve ได้
```

**identity ก็มี sequence** และ `pg_get_serial_sequence` ก็หาเจอ · ที่ฐานจริงนับได้ 48
ไม่ใช่เพราะ identity มองไม่เห็น แต่เพราะ **ตารางนั้นยังไม่มีอยู่ในฐานที่วัด** — ผมยืนยัน:

```
t98b / t115 / t125 / t122 :  sequences 48 · directory_sync_checkpoints exists = false
```

migration `20260902130000` เป็นของใหม่ (31 migration directory วันนี้) และยังไม่ถูก apply
ลงฐานที่ recon วัด · **"48 vs 49" คือความต่างระหว่างสคีมาปัจจุบันกับฐานที่ล้าหลังหนึ่ง
migration ไม่ใช่ object ที่ถูก drop**

### ผลต่อ RF-9 — **การนับ 49 เป็นออราเคิลที่ผิด**

เทสที่ assert *"ตรวจครบ 49"* จะ **แดงบนฐานที่ migrate ไม่ครบ** และ **เขียวด้วยเหตุผลผิด**
ถ้าวันหนึ่งมีคนเพิ่มตาราง identity อีกตัวแล้วตัวเลขบังเอิญยังเป็น 49

**สั่ง**: RF-9 ต้อง **derive จำนวนจากฐานที่กำลังทดสอบ** ไม่ใช่ค่าคงที่ —
enumerate `information_schema.columns WHERE is_identity='YES' OR column_default LIKE 'nextval%'`
แล้ว assert ว่า **ทุกแถวที่ enumerate ได้ถูกทดสอบจริง** · ค่าคงที่ที่ควรมีคือ
**"มากกว่า 40"** เป็น sanity floor ไม่ใช่ 49 เป๊ะ

**และต้องครอบ identity ด้วย** — `setval` ใช้กับ identity sequence ได้ แต่ `ALTER TABLE …
ALTER COLUMN … RESTART` เป็นทางที่ถูกกว่า · ถ้า restore ใช้ `pg_get_serial_sequence` +
`setval` มันจะทำงานกับทั้งสองแบบ **แต่ต้องมี fixture ที่มีตาราง identity อยู่จริง** ไม่งั้น
เส้นทางนั้นไม่เคยถูกรัน

## Open question 1 — cache invalidate เมื่อ `policy_versions` ถอยหลัง — **ผมตอบได้จากการอ่าน**

`FilterCache.get` (`cache.js:93-99`) เทียบแบบนี้:

```js
const head = String(await currentPolicyVersion(input.db ?? this.db));
const fresh = entry && entry.policyVersion === head && Date.now() - entry.storedAt < this.ttlMs;
```

**เทียบเท่ากัน ไม่ใช่มากกว่า** · `currentPolicyVersion` คืน `MAX(version)` ·
ดังนั้นเมื่อ restore ทำให้ version ถอยจาก 100 → 50:

- entry ที่ stamp ไว้ 100 **ไม่ตรงกับ head=50 → ถือว่า stale → rebuild** ✅
- **ไม่มีหน้าต่างที่ serve grant ที่ถูกเพิกถอน** เพราะการไม่ตรงกันไปทางไหนก็ตาม = miss

**คำตอบ: ปลอดภัยโดยบังเอิญ และเป็นความบังเอิญที่ควรถูก pin ด้วยเทส** ·
คอมเมนต์ที่ `cacheSubscriber.js:10-13` อ้างว่า version check คือ "belt and braces" คู่กับ
event — **ในกรณี restore มันคือ belt ตัวเดียว** เพราะไม่มี `policy.changed` event ถูก
publish ระหว่าง restore (ไม่มีใครเรียก `bumpVersion`)

**สั่ง**: RF ใหม่ — restore ที่ทำให้ version ถอยหลัง แล้ว assert ว่า entry เก่าไม่ถูก serve ·
**และ** assert ว่าถ้าเปลี่ยนการเทียบเป็น `entry.policyVersion <= head` เทสจะแดง
(นั่นคือ mutation ที่พิสูจน์ว่า "เท่ากัน" เป็นสิ่งที่ load-bearing ไม่ใช่รายละเอียด)

**ข้อควรระวังที่ยังเปิดอยู่**: `FilterCache` เป็น process-wide (`cacheSubscriber.js:19`) ·
ถ้ามีหลาย process การ restore บนเครื่องหนึ่งไม่ส่งสัญญาณไปอีกเครื่อง — **แต่การเทียบ
version อ่าน DB ทุกครั้ง** จึงยังปลอดภัย · **ยืนยันว่านี่คือเหตุผลที่ `FilterCache.get`
ยอมจ่ายค่า round trip ทุกครั้ง** ตามที่คอมเมนต์เขียนไว้ — และ restore เป็นเคสที่ทำให้
การตัดสินใจนั้นคุ้มที่สุด ควรเขียนไว้ในคอมเมนต์นั้น
