# QA-3 evidence — #80 `719b7eee` (route lane) — FAIL

Author: QA-3 (anything-llm-ea). Worktree `/tmp/qa3-80r`, own `yarn install` +
`prisma generate`, own database `qa3_80`. Probes written independently of Dev3's
tests and run against the real route stack and the real SMTP fixture.

Everything ruling D asks for is implemented and behaves — except that the rate
limiter it specifies is **not mounted on any route**.

## BLOCKER — `inviteMailRateLimit` is built, exported, and never used

`grep -rn "inviteMailRateLimit"` over the whole server, excluding
`node_modules`, returns four hits and all four are inside
`utils/middleware/requestControls.js`: the `limiter()` call at :239 and the
export at :317. Same for `mailerTestRateLimit` (:249, :321).

The two invite routes carry no limiter:

```js
// endpoints/admin.js:273
app.post("/admin/invite/new",
  [validatedRequest, requirePermission("invite.create", orgResource),
   simpleSSOLoginDisabledMiddleware], …)

// endpoints/api/admin/index.js:317
app.post("/v1/admin/invite/new",
  [validApiKey(scopeFor("POST", "/v1/admin/invite/new"))], …)
```

Measured end to end, through the real route, with the channel verified: **fifteen
consecutive mailed invites from one session all returned 200 and all fifteen were
delivered to the fixture.** The configured ceiling is 10 per minute.

```
QA3B flood: 15 requests -> 15 accepted, 0 refused (limit default is 10)
QA3B statuses: 200,200,200,200,200,200,200,200,200,200,200,200,200,200,200
```

Ruling D says invite-by-email "is rate limited per key/org rather than per IP".
It is not rate limited at all. This is the exact shape the ruling exists to
prevent — one credential spending a deployment's sending reputation without a
ceiling — and the comment above the limiter states that case in full while
nothing enforces it.

The limiter's own logic is correct; only the wiring is missing. Everything in the
next section was verified by mounting `inviteMailRateLimit` on a stub route,
which is also how Dev3's own tests exercise it — and that is why no test caught
this. `__tests__/requestControlsHttp.test.js` asserts on `actorKey` directly and
never asks whether any route uses it.

**Fix:** add `inviteMailRateLimit` to the middleware array of
`POST /admin/invite/new`, and `mailerTestRateLimit` to the SMTP test endpoint
when that route lands. **Test that would have caught it:** the flood above —
drive the real route past the ceiling and assert a 429, rather than testing the
limiter in isolation.

## Everything else passes

### Rate-limit bucketing (correct logic, unreachable)

| id | scenario | result |
|---|---|---|
| C1 | two API keys, one IP | `200,200,429` each — separate buckets |
| C2 | one key, three IPs | `200,200,429` — rotating address buys nothing |
| C3 | session token reissued for the same user | `200,200,429` — the new token shares the bucket |
| C4 | two different users, one IP | `200,200,429` each |
| C6 | ceiling raised mid-process | takes effect immediately (#77 holds) |

C2 and C3 are the two failures the design set out to avoid, and neither occurs.

C5, recorded as a consequence rather than a defect: a token with a forged `id`
and an invalid signature **does** get its own bucket, because `actorKey` decodes
without verifying. Four rotating forged ids were all served. That is safe as
written — `validatedRequest` rejects the forgery downstream, so the attacker
spends a bucket and still gets 401 — but it means the limiter alone bounds
nothing for an unauthenticated caller who can vary the claim. Worth stating in
residual, since the code comment argues the case and a reader may take it as
"forged tokens are limited".

### The SMTP password does not leak, in any encoding

`AUTH PLAIN` puts the credential on the wire base64-encoded, so grepping logs for
the raw string proves nothing. Measured all three forms:

```
A1 raw password on wire?            false
A1 AUTH PLAIN blob on wire?         true      <- as it must be
A1 bare base64 of password on wire? false
A2 raw password in logs?            false
A2 base64(AUTH PLAIN) in logs?      false
A2 base64(password) in logs?        false
A2 invite code in logs?             false
```

A2 captured `console.log/error/warn` across a real send and additionally forced
`JSON.stringify(driver)`, `util.inspect(driver)` and template interpolation —
the two shapes QA-1 found leaking before. Both are covered: `toJSON` is an
allowlist and the inspect symbol replaces the password with `[redacted]`.

A3: with the fixture answering `535`, the driver throws
`NotificationConfigurationError — The mail server rejected these credentials.`
and neither the message, the error object, nor any log line contains the
credential that was rejected.

### One address per request, and no header injection

Eight malformed shapes, each refused with 4xx and **no invite row created**:

| input | status | error |
|---|---|---|
| `["a@x.com","b@y.com"]` | 400 | Send one invitation at a time. |
| `"a@x.com, b@y.com"` | 400 | The email address is not valid. |
| `"a@x.com;b@y.com"` | 400 | " |
| `"a@x.com\r\nBcc: evil@z.com"` | 400 | " |
| `"a@x.com\nBcc: evil@z.com"` | 400 | " |
| `"<a@x.com>, <b@y.com>"` | 400 | " |
| `42` | 400 | " |
| `{address:"a@x.com"}` | 400 | " |

Control: one good address returns 200 and the fixture transcript contains exactly
one `RCPT TO`. Without it, a route refusing everything would pass this table.

The CRLF rows matter most: a header-injection attempt is rejected by the address
regex before anything reaches the transport, so `Bcc:` never becomes a header.

### Channel state, verified at send time

| scenario | result |
|---|---|
| stored hash does not match | **409**, no invite created |
| one connection field changed after verification (`smtp_port`) | **409** |
| password rotated, every stored field untouched | **409** |

The third is the one a settings-only hash would miss. `configHash` is an HMAC
over `SIG_KEY` covering the password and every connection field, so rotating the
credential invalidates the proof by construction.

### `/v1` mints links only

`POST /v1/admin/invite/new` with `email` and a key carrying `invite.create`,
`user.manage` and `system.write`: **400**, zero `RCPT TO` on the fixture, error
naming the reason. An API key cannot mail from this deployment's domain even when
its creator could.
