## The two things PMO asked

### (a) `readFromAssertion` never touches `doc` — and the reason it works is structural

Confirmed, and the implementation is stronger than what I asked for. I asked for reads to
be *anchored* at the verified node; what landed is a helper that **closes over no document
at all** (`index.js:63-68`), so a document-wide read is not something a caller can express
rather than something they are asked not to write. The comment says exactly that. It is the
difference between a rule and a mechanism.

Every read is accounted for. `_verifiedAssertion` is the only function that touches `doc`,
it returns the element, and every subsequent method takes the element:

| read | anchor |
|---|---|
| `Conditions/@NotBefore`, `@NotOnOrAfter` | `./` on assertion |
| `Conditions/AudienceRestriction/Audience` | `./` on assertion |
| `Subject/SubjectConfirmation/SubjectConfirmationData/@InResponseTo` | `./` on assertion |
| `Subject/NameID/text()` | `./` on assertion |
| `AttributeStatement/.../displayName`, `groups` | `./` on assertion |
| `assertion.getAttribute("ID")` for the claim | the element itself |

No `//` survives outside `_verifiedAssertion`. `grep` on the file confirms it.

The generalized fixtures are the part that makes this real rather than asserted. I asked
for siblings of `xswUnwrappedSubject` for the other checked fields; all three exist
(`xswUnwrappedConditions`, `xswUnwrappedAudience`, `xswUnwrappedInResponseTo`) built on one
`xswUnwrappedElement` primitive, each planting a valid-looking element ahead of an assertion
that genuinely **fails that same check** — expired, wrong audience, wrong InResponseTo. That
construction is right: the assertion stays valid and signed so all three assertion-level
guards still pass, isolating the document-order read and nothing else.

**The best thing in this commit is a correction Dev3 made unprompted and recorded.** The
first version of two fixtures planted a *bare* `AudienceRestriction` / `SubjectConfirmationData`
— which the driver's read path cannot reach even document-wide, so they passed against the
unsafe mutant and proved nothing. They now plant a full `Conditions` / `Subject` matching the
path shape actually read. That is a fixture that was green for the wrong reason, caught by
running the mutant rather than by reasoning about it (§7.9), and the ledger says so. Both
mutants (`claim` hoisted; `readFromAssertion` document-wide) kill exactly the intended tests
and nothing else.

### (b) Order: verify → ID-match → conditions → claim

Confirmed, in that order, at `completeLogin:148-162`. Comments mark the four steps and rule 2
is stated at the top of the file as the attack it prevents rather than as a convention.

The tests pin it as an ordering property, not as a code shape, which is what makes it
durable:

- signature failure records nothing;
- **expired records nothing** — this is the one that matters. Signature-first alone is not
  sufficient: an attacker holding a genuinely-signed expired assertion could still burn its
  ID if the claim ran between verify and conditions. That test is the difference between
  "claim is not first" and "claim is last";
- wrong audience records nothing;
- **the burn attack, end to end**: attacker presents the victim's real assertion ID with a
  non-IdP signature, is refused, and the victim's genuine login afterwards still succeeds.
  That is the ruling stated as its attack;
- **a successful login DOES record the ID** — the counterweight. Without it, "records
  nothing" is satisfied by a driver that never records at all and the replay defence is gone.

`expiresAt` comes from `this._notOnOrAfter(assertion)`, read from the verified node, so an
attacker cannot set the row's lifetime. That was the third ordering point I raised and it is
handled.

`fixtures.valid` was also fixed to honour an explicit `assertionId` and sign a reference to
**that** ID (`assertions.js:108-116`) — without it the burn test would have signed a reference
to an ID the document does not contain, and would have passed for the wrong reason.

## FINDING-1 (must close before the ACS route) — `Destination` and `Recipient` are never checked

The driver stores `acsUrl` (`index.js:101`) and never reads it. Neither
`Response/@Destination` nor `SubjectConfirmationData/@Recipient` is validated, though the
fixtures emit both.

These are the checks that stop an assertion captured at one endpoint being replayed at
another — a second AnythingLLM instance behind the same IdP, or a staging ACS whose logs an
attacker can read. `InResponseTo` narrows it but does not close it: an attacker who can
observe a login they initiated at endpoint B holds a matching request ID.

`@Recipient` is inside the assertion and is the more important of the two, since it is signed
and must be read via `readFromAssertion`. `@Destination` is on the Response element — outside
the signature — so it is advisory and worth checking only as a cheap early refusal, never as
a trusted claim. Both belong before the claim.

## FINDING-2 (must close before the ACS route) — the Issuer is never checked

`idpEntityId` is stored (`index.js:99`), used once in `validateConnection`'s success detail,
and never compared against `Assertion/Issuer`.

The signature check is what mostly covers this — an assertion is only accepted if a
configured certificate signed it — so this is defence in depth rather than an open door
today. It stops mattering the moment a deployment configures two providers, or one provider
whose certificate list overlaps another's, at which point the driver would accept an
assertion from IdP B under provider A's identity.

One line, read from the verified assertion:

```js
const issuer = readStringFromAssertion(assertion, "string(./saml:Issuer/text())");
if (issuer !== this.idpEntityId) throw new IdentityAuthenticationError(REFUSED);
```

Recording both as ACS-route acceptance criteria rather than as blockers on this SHA: the
driver is not reachable until a route calls it.

## NIT-1 (low) — `samlp:Status` is not checked

A `Response` carrying `StatusCode = Responder` or `AuthnFailed` with no assertion is a
normal IdP outcome. Today it falls through to `assertions.length !== 1` and produces the same
flat `REFUSED`, which is safe — but an operator debugging a failing IdP gets no signal that
the IdP itself refused. Worth reading Status into the *log* line, never into the response.

## NIT-2 (low) — `_checkConditions` accepts an assertion with no `Conditions` NotBefore

`notBefore` is optional (`if (notBefore && ...)`), which matches the SAML spec. Combined with
`_checkAudience`, which requires `Conditions/AudienceRestriction/Audience` to contain our
entity ID, an assertion with no `Conditions` element at all is already refused — so this is
correct as written. Recording it only because the two checks are load-bearing for each other
and neither says so: if `_checkAudience` were ever relaxed, `_checkConditions` would accept
an assertion with no validity window at all.

## NOTE — clock skew is applied to both bounds

`CLOCK_SKEW_MS = 3 min`, applied as `now >= notOnOrAfter + skew` and
`now < notBefore - skew`. Correct: skew must widen the window in both directions or a
correctly configured IdP trips it. Three minutes is a reasonable choice and the comment
justifies it. Worth making configurable eventually, not now.

## Also verified

- **NOTE-A closed**: `"id" TEXT NOT NULL DEFAULT gen_random_uuid()::text`. Raw-SQL inserts
  now work, and the comment names why Prisma's client-side `@default(uuid())` was not enough.
- **NOTE-B/C closed**: the PG13+ requirement is stated as a comment with the deployed stack
  named (PG16, verified by query rather than assumed), and `WHERE email <> normalize(email, NFC)`
  makes a re-run a no-op. No `DO` block — right call, since the version question was answered
  rather than defended against.
- **Certificate rotation**: `_verifyAgainstConfiguredKeys` loops every certificate and
  `continue`s on both a false return and a throw, so a malformed certificate in the list
  cannot deny a login the next one would accept. Tested with an old+new list. This is what
  makes `certificates TEXT[]` an operational feature rather than a column shape.
- **Empty certificate list throws at construction**, tested. "No certificate configured"
  never reads as "accept anything".
- **The key never comes from `KeyInfo`** — `publicCert` is always `this.certificates[i]`.
  Tested from both sides via `selfSignedWithKeyInfo`.
- **One refusal message** (`REFUSED`) for every failure path, detail to logs only. An
  unauthenticated caller cannot distinguish expired from replayed from wrong-audience, which
  is §3.4's rule for this surface.
- **Boundaries hold**: the driver requires `prisma` only for the replay store, and the test
  file says that in a comment as a tripwire. `refreshPrincipal` / `listPrincipals` /
  `listGroups` throw `IdentityCapabilityError`, so the capability flags are not decoration.
  `revokeSession` is idempotent per the seam.
- **`subject` is the NameID, not the email** — a changed address does not become a different
  person. `emailVerified: true` is justified in a comment (the IdP asserting the address IS
  the verification, which the signature just established) rather than assumed.
- **`groups` are read but marked as observations**, with R2 keeping role assignment out of
  drivers entirely.
- Registry uses `Object.create(null)` and both drivers register by `providerId()`.
