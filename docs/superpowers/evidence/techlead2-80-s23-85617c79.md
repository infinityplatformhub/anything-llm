## OBS-1 — implemented as a conditional `updateMany`, and it closes more than expiry

`markClaimed` now repeats the redeemability conditions in the `WHERE` clause and reads
`count`:

```js
const claim = await prisma.invites.updateMany({
  where: {
    id: Number(inviteId),
    status: "pending",
    OR: [{ expiresAt: null }, { expiresAt: { gt: now } }],
  },
  data: { status: "claimed", claimedBy: user.id },
});
if (claim.count !== 1)
  return { success: false, error: "Invite not found or is invalid." };
```

That is the shape I proposed, including the `expiresAt: null` arm that keeps copy-link
invites working. The comment states the reason I gave — the read that preceded it happened
at a different instant — which matters because a future reader would otherwise see the
expiry check in `Invite.get` and read this one as redundant.

The route handles the new failure honestly (`endpoints/invite.js`): when the claim loses,
the user row exists but owns nothing the invite granted, so answering success would be a lie
about workspace access. It returns the flat refusal and logs.

**The pre-existing double-claim hole closes with it.** I flagged that two simultaneous POSTs
both passed the status check and both called an unconditional `update`, the second silently
overwriting `claimedBy`. The test drives it directly:

```
✓ two simultaneous redemptions of one code produce exactly one account
```

Mutation, reverting to the unconditional `update`: **2 failed / 10**.

## OBS-2 — the comment is there, and it names `deactivate` specifically

`Invite.get`'s new header says the expiry rule is for redemption only, and calls out both
paths that must not inherit it: `deactivate` (an admin tidying an expired invite) and the
admin listings (which must still answer "did this invite ever get used?"). That was the
exact risk — a tidying pass unifying two lookups that differ on purpose — and naming the
functions is what stops it.

## M3 — the regression I was most worried about is covered

Every invite that exists today has `expiresAt: null`, so reading null as expired would
retire all of them while every new mailed invite kept working — invisible to a test suite
written around the new feature.

The schema comment is explicit that there is **no `@default`** on `expiresAt`, with the
reason ("a default would retire every invite already in the table the moment the migration
ran"). `Invite.get` guards on `invite.expiresAt &&`, and the test asserts it end to end:

```
✓ M3: a copy-link invite with NO expiry still works
```

Mutation, `if (!invite.expiresAt || …)`: **3 failed / 10**.

## M2 — Dev3's "equivalent" claim is correct, and I checked it

Changing `<=` to `<` leaves the suite green. That is a surviving mutant, so I looked at
whether it is reachable rather than accepting the report:

```
expiresAt === now  ->  <= says expired: true  |  < says expired: false
```

The two differ only when `expiresAt.getTime()` equals `Date.now()` to the millisecond. The
value is written by `Invite.create` as `Date.now() + 7 days` or supplied by an admin; hitting
the same millisecond as the redemption request is not a state a test can arrange without
freezing the clock, and neither behaviour is wrong at that instant — an invite that expires
exactly now may be honoured or refused. **Equivalent mutant, confirmed, not a coverage gap.**

The boundary is still tested in the way that matters — five seconds ahead is valid, one
second past is not, both directions — which is what catches a genuine off-by-one (a
comparison against the wrong operand, or a sign flip).

## The redemption oracle — closed, with the strongest available assertion

This is the best test in the change. `POST /invite/:code` used to answer a username collision
differently from an unknown code, so reaching `User.create` at all confirmed a live invite to
anyone willing to guess, without redeeming it.

Three things make the fix hold:

1. `User.validateNewCredentials` runs **before** the invite is looked at, so caller-fixable
   input is still reported (someone retyping a rejected password needs to know why) without
   that answer depending on whether the code was real.
2. Everything after the lookup collapses to one `refusal` object — unknown code, expired,
   claimed, username taken, lost race.
3. The test compares **`response.text`**, not the parsed body:

```js
expect(response.text).toBe(responses[0].text);
```

Key order and whitespace are observable to an attacker and invisible to `toEqual` on a
parsed object. That is the correct assertion for an oracle test and I would not have thought
to ask for it.

Mutations: leaking `User.create`'s error again → **1 failed**; moving
`validateNewCredentials` after the lookup → **1 failed**; answering success on a failed claim
→ **1 failed**.

## O1 — `validateNewCredentials` is pure, verified by execution and by grep

```
malformed username -> "Username must be at least 2 characters"
weak password      -> "password should be at least 8 characters long"
both fine          -> null
```

No database is reachable in that path: grep over the function body finds no `prisma`,
`findFirst` or `findUnique`, and the only caller is `endpoints/invite.js:46`. The header says
it is *"PURE by requirement, not by accident"* and that it must never report whether a
username is TAKEN — which is the property that keeps the oracle closed, since availability is
a fact about the database and belongs behind the flat refusal.

**One mutant survives here and should not be read as a gap.** Appending dead code after the
`return null` leaves the suite green, which is expected — unreachable code changes nothing.
There is no mutation that makes this function report a taken username without also adding a
database call, and the grep is what covers that.

## Also correct

- `Invite.create` enforces the email/expiry pairing **in the model**, where both creating
  routes pass through, rather than at either route. The explicit-`expiresAt` escape (an admin
  choosing 24 hours) is distinguished from "not supplied" with `expiresAt !== undefined`,
  so passing `null` deliberately is not silently overridden by the 7-day default.
- The `#71` migration disables every `pending` invite, and its comment states the blast
  radius and the cost plainly: legitimately-issued unredeemed invites stop working and must be
  reissued. It also says what it does **not** undo — codes already exported are out
  permanently; disabling removes their use, not their exposure. That is the right framing,
  and it matches the recommendation I made on the S11 leak recon: revoke the credential rather
  than scrub the append-only log.
- `requestControlsHttp.test.js` gained `INVITE_RATE_LIMIT_MAX` to the per-test cleanup list
  and now checks `"0"`, `"-5"` and `""` fall back to the built-in 30. `"0"` is the one a
  `Number.isFinite` guard would let through, and a limit of zero refuses every request — a
  self-inflicted outage rather than an open door, but an outage.
