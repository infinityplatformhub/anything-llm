## 2. O1 — the redemption oracle is closed

Four states over HTTP, compared as **raw text and `content-length`**:

| state | status | len | body |
|---|---|---|---|
| unknown / expired / claimed / disabled | 200 | 59 | `{"success":false,"error":"Invite not found or is invalid."}` |

**Byte-identical across all four.** The oracle I reported in pre-read is gone:

```
dup-username on VALID   code -> 200 len=59 identical
dup-username on UNKNOWN code -> 200 len=59 identical
```

Caller-fixable input still gets a useful message, and the same one either way:

```
weak password, unknown code -> "password should be at least 8 characters long"
weak password, VALID   code -> identical
```

## 3. O2 / O4 / OBS-1

- `Invite.get(expired)` → `null`; `deactivate(expired)` → `{success:true}` (per ruling)
- `email` present → `expiresAt` ~7 days; absent → NULL; explicit value wins (1h honoured);

| surface | result |

## NIT-1 — the mailed-invite pairing rule is unconstrained

M4 replaces `if (normalizedEmail && !expiry)` with `if (false)` and 29/29 stays green.
Not equivalent — measured under the mutation:

```
Invite.create({ email: "leak@example.com", expiresAt: null })
  -> CREATED  expiresAt=null  email=leak@example.com
```

Exactly the state the migration comment names: *"A link sent to an inbox and valid forever
is a bearer credential sitting in mail history."* The rule is correct; nothing would notice
its removal.

Cause is reachability: no route passes `email` to `Invite.create` yet, and the invite suite
is HTTP-driven, so the rule cannot be reached from it. A model-level case fixes it:

```js
await expect(
  Invite.create({ createdByUserId: 1, workspaceIds: [], email: "x@example.com", expiresAt: null })
).resolves.toMatchObject({ invite: null });
```

Worth adding **before** the stage that wires `email` into the routes — that is when an
unnoticed regression becomes reachable by an admin.

## NIT-2 — the driver object serializes its own password

The password is held as a plain property (`SmtpNotificationDriver.js:62`) with no `toJSON`
and no custom inspect, so the object hands it to any serializer:

```
JSON.stringify(driver)                    LEAK
util.inspect(driver)                      LEAK   (this is what console.log does)
util.inspect({driver}, {depth: 5})        LEAK
util.inspect(new Error("x", {cause:driver})) LEAK
String(driver)                            clean
```

The suite asserts the password is absent from console output, from error messages, and from
`status().details` — all true — but never serializes the **driver itself**. So the covered
paths are the ones where the driver was careful, and the uncovered one is where care was
delegated to every future caller: one `console.error("smtp failed", driver)` or one driver
attached as an error `cause` prints the credential.

The file's own rule is *"It cannot be logged, cannot appear in an error message"* — this is
the shape that makes that rule enforceable rather than remembered:

```js
toJSON() { return { host: this.host, port: this.port, secure: this.secure, username: this.username }; }
[require("util").inspect.custom]() { return this.toJSON(); }
```

Not a blocker: nothing in the codebase serializes a driver today. It is a NIT because the
protection currently depends on no one ever doing so.
