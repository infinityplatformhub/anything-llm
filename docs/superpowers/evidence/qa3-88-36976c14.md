#87 taught the resolver to accept `VECTOR_DB=PINECONE`; eight providers then
still compared the raw string inside `connect()` and threw
`Provider::Invalid ENV settings` for a spelling the app had just accepted. This
closes that.

## The set is discovered, not listed

```
Q1 providers with a VECTOR_DB guard (8): astra, chroma, chromacloud, milvus,
                                         pinecone, qdrant, weaviate, zilliz
Q1 providers with NO guard: lancedb, pgvector
```

Enumerated from the provider directory, not from a hardcoded array, so a ninth
guard added later appears here without anyone updating a list. `lancedb` and
`pgvector` genuinely have no such guard — they are the two whose `connect()` does
not read `VECTOR_DB` at all — so eight is the whole population, not a subset
someone chose.

`zilliz` is the one worth naming: it `extends Milvus` and overrides `connect()`
with its own guard, so a fix applied to Milvus alone would have missed it while
looking complete.

## The guards behave

Each of the eight, with `VECTOR_DB` set to its own name in four spellings —
exact, upper, capitalised, space-padded — `connect()` called for real:

```
Q3 guards rejecting a spelling the app accepts: none
```

Failing for the provider's *own* reasons (no host configured, connection
refused) is fine and expected; what must not happen is `Invalid ENV settings`,
which tells an operator their configuration is wrong when only its capitalisation
differs.

Control, so Q3 is not vacuous:

```
Q4 guards that did NOT refuse a foreign selection: none
```

With `VECTOR_DB=lancedb` — never one of the eight — every guard still throws
`Invalid ENV settings`. The guards still do their job; they just no longer do it
to spellings the resolver honours.

```
Q5 spellings the normaliser maps elsewhere: none
```

Each guard's own key is what `normalizeVectorDbKey` produces for all four
spellings of that provider's name, so the guard and `getVectorDbClass` cannot
disagree about which provider is selected.
