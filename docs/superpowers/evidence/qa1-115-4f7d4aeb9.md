M1 and M2b are red on **different** tests, which is the property that matters here: the fallback test only ever reaches `bootHTTP`, so without the dedicated bootSSL test (real self-signed cert, `https.request` because undici ignores `NODE_TLS_REJECT_UNAUTHORIZED`) the bootSSL hydrate could be deleted and the suite would stay green. The test file says this in its own comment and it is true — measured.

Both timing assertions are real: `expect(elapsed).toBeGreaterThanOrEqual(KEY_DELAY_MS * 3)` with a store that sleeps 200ms per key, plus `expect(reads.sort()).toEqual(Object.keys(STORED).sort())` so an empty store cannot satisfy the first. This is timing, not mock call order, as the ruling asked.

M3 surviving is **not** a hole. Measured the fallback path directly with a counting store:

```
bootSSL (no HTTPS_KEY_PATH) → catch → bootHTTP, reads = ["QA1_DBL_KEY"]
```

One read, not two: bootSSL hydrates before its `try`, the fallback into `bootHTTP` hydrates again, and with the real store both are the same rows — so dropping the injection from the fallback leaves the fallback test green because bootSSL's own pre-listen hydrate already populated `process.env`. Redundant-by-design, and the redundancy is correct (a direct `bootHTTP` call must hydrate on its own). Not worth a finding.

## NIT-1 — `each boot path calls it exactly once` scans source and says so, but still overstates

`__tests__/utils/helpers/credentialPersistence.test.js:190`

```js
expect(source.match(/await loadStoredCredentials\(/g)).toHaveLength(2);
```

The comment above it is honest — it records that the two previous assertions here were source scans that broke when the call took an argument, and that the real property moved to the timing test. Good. But the assertion that replaced them is still a source scan, and its name claims a runtime property ("each boot path calls it exactly once") that it cannot check:

- On the **fallback** path both calls run in one boot — measured above, `bootSSL` → catch → `bootHTTP` executes `loadStoredCredentials` twice. "Exactly once per boot path" is true per function, not per boot, and the name does not say which.
- It is defeated the same way M8b was on #30 slice 3: keep the two literals and add a third call through a variable (`const load = loadStoredCredentials; await load(store);`) and the count stays 2.

Fail-safe direction and the comment already scopes it as "a cheap duplicate/omission check", so this is naming, not behaviour. Suggest renaming to something that describes what it actually asserts — `the loader is referenced from both boot functions` — or dropping it, since M1/M2b already cover both paths behaviourally.
