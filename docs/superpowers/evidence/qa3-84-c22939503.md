## Why this SHA exists — the RED I recorded on the previous one

`f309f1247` added one test, `gates credential clearing exactly as it gates credential writing`. It
reads `endpoints/system.js` as text, extracts the permission each of the two routes asks for, and
asserts the two are equal. The extraction was:

```js
const at = source.indexOf(`"${route}"`);
const match = source.slice(at).match(/requirePermission\(\s*"([\w.]+)"/);
```

`slice(at)` runs to end of file. Nothing stops the search at the end of the route it started in.

**Mutation (M1): delete the middleware line from the DELETE route entirely** —
`[validatedRequest, requirePermission("system.write", orgResource)]` → `[validatedRequest]`.

```
✕ refuses a manager clearing a stored credential      Expected: 403  Received: 200
✓ gates credential clearing exactly as it gates credential writing     ← GREEN
1 failed, 9 passed
```

Ran the extractor standalone against that mutated source to name the mechanism rather than infer it:

```
DELETE  : action=system.write  routeAtLine=739  foundAtLine=764
POST env: action=system.write  routeAtLine=763  foundAtLine=764
```

Both routes read **the same line, 764** — the `update-env` gate. The equality test was comparing
`update-env`'s permission against itself, which is true no matter what the DELETE route does. A route
with no authorization at all satisfied the test whose entire purpose is to notice that.

The behaviour test caught the hole, so the fix was never in danger. What was in danger is the claim
the new test makes about itself: "moving one does not [pass]". On `f309f1247` that was false for the
one way of moving it that matters most — removing the gate rather than changing it.

## A note on M5 and the OpenAI mask test

M5 kills `leaves a secret untouched when the caller submits the masked placeholder` and **not**
`keeps a stored OpenAI key when an authorized actor submits its mask`. The second test survives its
own mutation. It is not testing what its name says.

Called `updateENV` directly with the filter removed:

```
updateENV({ OpenAiKey: "****" })          → {"newValues":{},"error":"OpenAI Key must start with sk-"}
                                             OPEN_AI_KEY after: sk-live-original   (unchanged)
updateENV({ LMStudioTokenLimit: "****" }) → {"newValues":{"LMStudioTokenLimit":"**********"},"error":false}
                                             LMSTUDIO_MODEL_TOKEN_LIMIT after: ****  (overwritten)
```

`OpenAiKey` carries `checks: [isNotEmpty, validOpenAIKey]`, and `validOpenAIKey` refuses anything not
starting with `sk-`. Asterisks are refused by the *validator*, not by the placeholder filter. The key
the other test uses, `LMStudioTokenLimit`, is chosen at runtime precisely because it has no hooks —
so it reaches the filter, and it is the test that actually covers the filter.

This is not a defect and I am not asking for a change: the OpenAI test still documents a real
user-visible guarantee (the UI's mask resubmission does not destroy a stored OpenAI key), and it
would go red if `validOpenAIKey` were dropped. But its name attributes the protection to the wrong
mechanism, and if `OpenAiKey`'s validator is ever relaxed the test will keep passing while the
guarantee moves onto the filter alone. Worth a one-line comment, not a rework.
