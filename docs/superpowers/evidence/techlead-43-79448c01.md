## (i) Does the verifier bind the element it READS to the element the signature COVERS?

**For the three XSW shapes in the fixture file: yes. In general: not yet — see FINDING-1.**

`samlLibraryEvaluation.test.js:44-81` does the right thing structurally, and it is the
right shape for the driver to inherit:

1. exactly one `//ds:Signature` (`:41`) — a second signature is a second answer;
2. `checkSignature` against the configured public key (`:47`);
3. **the references the verifier actually validated** are read back out of the library
   (`getReferences()`), normalized from either the `#_id` or the resolved-xpath spelling,
   and required to be exactly one (`:53-67`);
4. exactly one `//saml:Assertion` (`:69-71`);
5. **that assertion's `ID` must equal the signed reference id** (`:74-77`).

Step 5 is the actual XSW defence and it is present. Steps 1 and 4 are what make the three
fixtures throw rather than return the genuine NameID — all three (`xswWrapped`,
`xswSibling`, `xswHidden`) put a second `saml:Assertion` in the document, so `:70` fires
before the ID comparison ever runs. That is a correct refusal, and the tests assert the
strong form (`vouched` is `null`, not merely "not the forged id").

### FINDING-1 (medium, pre-driver) — the NameID is read from the DOCUMENT, not from the verified element

`:79`:

```js
const nameId = select("string(//saml:Subject/saml:NameID/text())", doc);
```

That xpath is rooted at the document, and XPath `string()` of a node-set takes the **first
node in document order**. The binding established at step 5 is on the *Assertion*; the read
at step 79 is not scoped to it.

Today that is masked by the `assertions.length !== 1` guard. It stops being masked as soon
as the forged `Subject` is not wrapped in an `Assertion`. Using this commit's own
`xswHidden` shape, with the forged assertion replaced by a bare Subject:

```xml
<samlp:Response>
  <samlp:Extensions>
    <saml:Subject><saml:NameID>attacker@example.com</saml:NameID></saml:Subject>
  </samlp:Extensions>
  <saml:Assertion ID="_real">...person@example.com...<ds:Signature .../></saml:Assertion>
</samlp:Response>
```

Every check passes — one signature, valid; one reference; **one** assertion; its ID equals
the signed reference — and `string(//saml:Subject/saml:NameID/text())` returns
`attacker@example.com`, because `Extensions` precedes the assertion in document order.
Nothing in the parser validates the response against the SAML XSD, so a `Subject` outside
an `Assertion` is just an element.

The fix is one character of scope, not a new rule: select **from the verified assertion
node**, not from `doc`.

```js
const verified = assertions[0];
const nameId = select("string(./saml:Subject/saml:NameID/text())", verified);
```

The same applies to every other claim the driver will read — `Conditions`,
`AudienceRestriction`, `SubjectConfirmationData/@InResponseTo`, `AttributeStatement`. The
rule for S2's driver, stated once: **after step 5, `doc` is out of scope. Every subsequent
read is relative to the verified assertion node.** The existing fixtures cannot catch this
because they all forge a second *Assertion*; add a `xswUnwrappedSubject` fixture in the same
shape as above so the rule has a RED failure behind it (§7.9).

I am calling this medium and not a blocker because it is in an evaluation harness, not in
shipping code — but it is the shape the driver is meant to copy, so it must not ship as
written.

### Smaller notes on the verifier

- `getReferences?.() ?? verifier.references ?? []` — if a future `xml-crypto` renames both,
  this silently yields `[]`, `signedIds.length !== 1` throws, and the failure looks like a
  malformed assertion rather than a broken integration. Acceptable (it fails closed), worth
  a comment.
- Step 2 verifies against a PEM passed by the caller. The driver's version must take the key
  from configuration only, never from the assertion's own `KeyInfo`/`X509Certificate` — the
  fixtures embed one (`assertions.js:91-94`) and copying the harness without noticing would
  be the alg-confusion equivalent for SAML. Flagging now so it is decided rather than
  inherited.
- Fixtures generate a keypair per run (`makeIdpKeypair`), so a verifier that "passes" by
  skipping signature checks cannot pass. Correct, and worth keeping when the driver lands.
- `expired`, `notYetValid`, `wrongAudience`, `wrongInResponseTo` fixtures exist with no test
  yet — expected at this slice; they are the DoD 4/5/6/8 hooks.

## (ii) Does the derived-handle line open a hole? Two cases checked.

**Both closed on this SHA.**

### (i) An SSO-linked account from ANOTHER IdP with a matching email

Closed, and this is the change from `40ef6112`. The check order is now fixed and the order
*is* the rule (`linkPrincipal.js:89-152`):

- **(1a)** `identity_links.findFirst({ where: { email: normalizedEmail } })` → refuse with
  *"already linked to another identity"*.
- **(1b)** local account stored under the raw address → R1's *"account with this email
  already exists"*.
- **(2)** derived-handle match, and only when `identity_links.length === 0`.

On `40ef6112` the handle rule ran first and used `identity_links.length === 0` as its
"different person" marker — so an account federated to a *different* provider under the
*same address* looked like an unrelated handle-sharer and fell through to the suffix retry,
creating a second local account for one mailbox. The new order forbids that, and
`linkPrincipal.test.js` "PMO ruling 2" pins it with `users.count()` unchanged. Reversing the
order kills that test, which is the mutation proof PMO asked for.

The distinction Dev3 drew (handle-match is takeover only for LOCAL accounts) is correct and
is now safe *because* it runs third: by the time `identity_links.length === 0` is consulted,
both email-based refusals have already fired, so the marker is only ever answering the
question it can actually answer.

### (ii) Case and Unicode normalization before comparison

Closed. `normalizeForCompare` (`deriveUsername.js:45`) is `NFC` **then** `toLowerCase`, it
is the first thing `sanitize()` calls, and `linkPrincipal.js:66` sets `normalizedEmail` from
the same function — so both sides of every comparison go through one implementation. NFC
before lowercase is the correct order (`İ`-class edge cases aside, which cannot reach a
handle: they sanitize to `-`).

Why NFC matters here concretely, since the comment states it but the mechanism is worth
recording: composed `é` is one non-matching character → `-`; decomposed `é` is
`e` plus a non-matching combining mark → `e-`. Without NFC the same person from an
NFD-emitting IdP derives a different handle than the account they own. Pinned by the
`café`/`café` test.

The stored side needs no normalization of its own: `users.username` is constrained to
`^[a-z][a-z0-9._@-]*$` (`models/user.js:20`), so a stored username cannot contain
non-ASCII in the first place, and Prisma's `mode: "insensitive"` covers the case half.
That is a real reason, not a coincidence — but it is load-bearing and undocumented. Worth
one line in the comment, because if the username regex is ever widened the comparison
silently becomes one-sided again.

### NIT-1 (low) — legacy `identity_links.email` rows are lowercase-only

S1 wrote `email: String(email).toLowerCase()` with no NFC (`linkPrincipal.js:66` on
`d4baf1ca`). Rows written before this commit are therefore in whatever form the IdP sent.
An NFD-form address stored then, arriving NFC now, misses (1a), misses (1b), and passes (2)
— a second account for one mailbox, the exact outcome (1a) exists to prevent.

Requires a non-ASCII email address **and** a pre-existing link row, so the reachable
population is small and probably empty. Either a one-line backfill
(`UPDATE identity_links SET email = normalize(email, NFC)` — PostgreSQL 13+ has
`normalize()`) or a recorded residual. Not a blocker.

### NIT-2 (low) — `usernameCandidates` exhaustion returns a Conflict

`linkPrincipal.js:180` throws `IdentityConflictError("Could not create an account…")` after
5 failed candidates. Each suffix is 4 random bytes, so exhaustion is not a collision — it is
a database problem wearing a conflict's error class, and `IdentityConflictError` routes to
"needs admin resolution / do not retry". `IdentityUnavailableError` (retryable) is the
closer fit. Cosmetic until something reads `.retryable`.

## Also verified

- `deriveUsername` prefixes rather than trims (`:64`), so `alice@`, `1alice@`, `_alice@`
  stay three handles — QA-1 NIT-1's actual fix.
- The suffix is never truncated; the base is trimmed to make room (`:88-90`). Truncating the
  suffix would reintroduce collisions in the mechanism that exists to resolve them.
- P2002-only retry (`:176`); anything else surfaces. Correct — a dead connection retried
  five times is five identical failures.
- `unusablePassword()` unchanged: bcrypt of 64 discarded random bytes.
- `syncLegacyRoleGrant` still runs before the link row is written, so no window exists where
  a user exists with a link and no grant.
- One derivation module shared by every driver, which is the point: OIDC and SAML deriving
  separately is how one person becomes two accounts.
