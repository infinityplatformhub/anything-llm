## Item 2 — two jest processes in parallel on one database

Both processes ran `__tests__/security/authorization` concurrently against `qa1_122`.

**With the 40-backend holder still up:** peak `total=54`, and **both** processes hit `sorry, too many clients already` — surfaced as `policy store failure:` out of `groupMembership.js:58` via `engine.js:96`. `engine.test.js` (2) and `routeWiring.test.js` (1) went red on it.

This is worth stating precisely, because it is a real limit and not a defect in the change: `connection_limit=5` bounds each **Prisma** pool, but a run also opens raw `pg` clients and per-suite isolated clients, so 40 held backends + 2 concurrent authorization runs still crosses 100 momentarily. The cap moves the ceiling; it does not make it unreachable. **Two parallel gate runs are safe; two parallel gate runs while something else holds 40 backends are not.**

**Without the holder:** peak `total=82` measured at 0.25s sampling over 2008 samples (run cut at my 10-minute tool limit, not by failure) — comfortably under 89, no `too many clients` at any sample.

## NIT-1 — M4: the wiring guard can be defeated the way #30 slice 3's M8b could

`__tests__/utils/test/connectionBudget.test.js`, `the setup file exists and calls $disconnect in afterAll`:

```js
expect(source).toMatch(/afterAll\(/);
expect(source).toMatch(/\$disconnect\(\)/);
```

Both are text matches on the file. Keeping the literal and making it unreachable —

```js
const noop = async () => {}; if (false) await prisma.$disconnect();
await noop();
```

— leaves the suite **12/12** while no pool is ever released. Same class as M8b on #30 slice 3 (change the action through a variable, keep the spelling), and the same class as the `each boot path calls it exactly once` scan I raised on #115.

The test's own comment is right that nothing behavioural can catch a missing side effect in a *later process*, and that is a fair constraint — but a **same-process** assertion is available and is not a source scan: the reconnect property this file already proves (`reconnects after $disconnect`) means the hook's effect is observable while the process is alive. A test that records `pg_stat_activity` backend count for this connection before and after the hook runs, or that spies on the real client's `$disconnect` from a suite ordered after one that used it, would fail on M4.

Fail-safe direction — a defeated guard makes gates slower and noisier, not wrong — so this is a NIT, not a blocker. Worth fixing because the guard exists specifically to stop the silent regression, and in its current form a refactor that moves the call behind a condition passes it.
