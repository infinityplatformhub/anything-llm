## Two errors of my own in this run

**My mutations N1 and N3 silently never applied on the first pass.** I wrote them as
`python3 -c "…"` inside bash, and the anchor strings contain backticks from the template
literal in the source — bash performed command substitution on them, the anchor no longer
matched, and the `assert` raised. The sweep printed the traceback and continued, so both
mutants reported "40/40 passed" for code that had never been touched. I nearly filed N1 as
a surviving mutant. Rewritten as quoted heredocs into `.py` files, with the applied diff
inspected before each run.

**My probe was a logger, not an oracle.** The first version printed every value and
asserted almost nothing, so N2 and N4 passed on my side while Dev1's suite went red — the
information was on screen and no test was reading it. I added 17 assertions (second key's
row survives, `newValues` holds exactly one key, `users` is 0, `mode` is not `"true"`,
`success` is `false`, statuses 500/200). The table above is from the assert-carrying
version; the earlier pass is not evidence of anything.

Both mistakes have the same shape and it is the one §7.9 is about: a check that cannot go
red is not a check. I am recording them rather than quietly re-running because the first
one in particular would have produced a confident, wrong finding.

## On the ruling

`delete newValues[key]` with `process.env` left live is the right split and the comment
says why. Worth noting the consequence plainly: the operator sees the key **absent** from
"changed" and an error naming it, while the running process is using the new value. That
is coherent — the value is in effect but not durable — but it is a state no single field
of the response expresses, and anyone reading `newValues` alone will conclude the write did
not happen at all. The `error` string is what carries the truth.
