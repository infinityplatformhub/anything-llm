## NIT-1 — the exempt set is not pinned; only the type is

Mutation (f) — replacing `if (isExemptPrincipal(actor)) return;` with `if (actor?.type !== "user") return;` — leaves the suite **43/43**.

That is the over-correction #123's RF-4 exists to catch in the sibling helper, and here nothing catches it. Measured consequence, with the mutant in place:

```
scoped api-key service actor, adding a user to an ACL-carrying group
  mutant     : ALLOWED
  clean tree : REFUSED
```

So a scoped API key — a `type: "service"` actor that is **not** an exempt principal — could rewrite the membership of a group carrying a document ACL. The existing RF-8 test `the exempt service principals still pass — coreJobs is not a user` proves the exempt principals are admitted, but nothing asserts that a non-exempt service actor is refused, so widening the check in that direction is invisible.

Not exploitable at this SHA: the mutant is the hole, not the code. But it is exactly the shape of the bug #123 shipped a fix for (`M-A`/`M-B` there went red in opposite directions precisely because both halves had tests), and the same two-sided pinning costs one test here:

```js
// a scoped api-key service actor is NOT exempt
await expect(addGroupMember({ actor: { type: "service", id: "api-key:1", orgId: 1 }, groupId: aclGroup.id, userId: victim.id }))
  .rejects.toThrow();
```

That kills (f) and makes the existing exempt-passes test mean something by contrast.
