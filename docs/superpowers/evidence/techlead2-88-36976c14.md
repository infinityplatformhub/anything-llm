## What I asked for on #87, and what landed

My #87 follow-up was that `getVectorDbClass` resolves `VECTOR_DB=CHROMA` to Chroma while the
provider's own `connect()` still compared raw and threw `Chroma::Invalid ENV settings` — so
`PGVECTOR` worked and `CHROMA` did not, for no reason an operator could see.

All eight guards now normalise. The comment on each says the part that matters: the message
was not merely unhelpful, it was **wrong about the cause** — the ENV settings are fine, and
nothing in that string points at capitalisation.

## The test discovers its subjects rather than listing them

`guardedProviders()` reads the providers directory, keeps every module whose source mentions
`VECTOR_DB` or `normalizeVectorDbKey`, and asserts the resulting set is exactly the eight.
A ninth provider added later with an unnormalised guard fails this suite rather than sitting
quietly outside it.

The comment names why that matters concretely: **zilliz's guard is at the top of `connect()`
rather than beside its client construction**, so a scan anchored on `new Client(...)` finds
seven. A fix applied from a short list would have left one provider resolving and then
throwing — and it is exactly the kind of near-miss this issue exists to close. I mutated
zilliz specifically for that reason (P3 below).

It also asserts `lance` and `pgvector` are **not** in the set, which is what stops the
discovery rule quietly widening.

## No SDK mocks, and the reason is right

Eight mocks of eight client libraries would be eight chances to pass for the wrong reason.
Instead the test calls the real `connect()` and asserts only that the failure is **not**
`Invalid ENV settings` — the guard runs before client construction, so a subsequent
"no endpoint / no API key" failure is the correct outcome and is treated as one.

That is the same discipline as #80's SMTP fixture: do not remove the thing under test in
order to test it.

## The require-cycle claim — corrected, and the tests kept for the right reason

The recon claimed a top-level `require("../../helpers")` in a provider would close a cycle and
hand back a half-built `module.exports`. The suite records that this was **measured and is
false**: `utils/helpers/index.js` requires providers only inside function bodies (the
`getVectorDbClass` switch arms), so nothing is required in that direction at load time, and
seven providers already require helpers at module scope today.

Keeping the tests anyway is the right call and the comment gives the reason: if someone later
hoists a provider require to helpers' module scope, the cycle becomes real, and these go red
before anyone debugs `normalizeVectorDbKey is not a function` at runtime.

I verified that guard works by making the cycle real — P4 adds
`require("../vectorDbProviders/chroma")` at helpers' module scope, and the lazy-require test
fails. The prediction is tested, not asserted.

## The two declared residuals — both real

**1. No test proves a guard-passing `connect()` actually succeeds.** Accurate. Every case
asserts on how `connect()` *failed*, since none of these stores is reachable from the test
environment. The property under test (the guard does not reject a valid spelling) is genuinely
covered, but "the provider then works" is not — and cannot be here without a live instance of
each. The real-store suites from #30 slices 1a/1b are where that lives, and they cover the
providers CI can run.

**2. Eight telemetry sites still read `VECTOR_DB` raw.** Confirmed by grep — every remaining
unnormalised read in `server/` is a label:

```
endpoints/api/openai/index.js:159      VectorDbSelection: process.env.VECTOR_DB || "lancedb"
endpoints/api/workspace/index.js:108, 736, 899
endpoints/chat.js:99, 218
endpoints/embed/index.js:96
endpoints/workspaceThreads.js:45
endpoints/workspaces.js:78
endpoints/utils.js:25                  vectorDB: process.env.VECTOR_DB || "lancedb"
```

None of them selects a provider or gates anything; they populate telemetry payloads and one
metrics endpoint. The consequence is that a deployment running `VECTOR_DB=Chroma` reports
`"Chroma"` while an identical one reports `"chroma"`, so aggregate counts split across
spellings. That is a data-quality problem in the telemetry, not a correctness or security one,
and leaving it out of a security-scoped change is the right boundary — provided it stays
recorded, which it is.

Worth noting `endpoints/utils.js:25` is slightly different from the other seven: it is a
metrics **response**, not a telemetry send, so an operator reading it sees their own raw
spelling — which is arguably more useful there than a normalised one.
