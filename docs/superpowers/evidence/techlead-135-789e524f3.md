## The three things I was asked to check

**One implementation of `revokeCredentialsFor` — CONFIRMED.** `grep -c "async function
revokeCredentialsFor" models/user.js` returns **1**. It is exported at `:583` and consumed by
`User.delete:472`, `User.update:346`, `endpoints/admin.js:207` and
`endpoints/api/admin/index.js:296`. Dev2 found their own regression — routing around `User.delete`
skipped the `revokedAt` stamp — and fixed it by **exporting and reusing** rather than
reimplementing, which is the correct repair: the comment at the call site says so
(*"reused, not reimplemented, so the stamp cannot drift between the two paths"*).

**The stamp is inside the same transaction — CONFIRMED.** Both routes:

```js
await prisma.$transaction(async (tx) => {
  await offboardUser({ actor, userId, db: tx });
  await revokeCredentialsFor(userId, tx);
  await tx.users.delete({ where: { id } });
});
```

`revokeCredentialsFor(userId, tx)` takes the transaction client, so the stamp, the offboard and
the delete commit or roll back together. The comment gives the right reason for one transaction
rather than two calls: *"a crash between them recreates the orphan by another route, which is the
same bug arriving through a narrower window."*

**The admin refusal is real — CONFIRMED, and asserted honestly.** The refusal role is
**constructed** (`user.manage` without `role.revoke`), because no seeded role has that shape — and
the fixture proves it built what it claims (`expect(held).toContain("user.manage")`,
`.not.toContain("role.revoke")`) before asserting anything. It matches on `/role\.revoke/` rather
than `/refused/`, because "refused" appears in unrelated errors and a fixture failing for another
reason would still match. The assertions are `status 200`, `success:false`, `orphanCount`
unchanged, **and the user row still present** — the comment notes that half is the one most often
omitted, and that a route which deleted the account and then failed to clean up would be worse than
today's behaviour. It also records that this route refuses *earlier*, at `validCanModify`, so 200 +
`success:false` is the route's existing shape and the 403 path is exercised by the API route
instead. Asserted as it behaves rather than bent to the expected status — right call, stated.
