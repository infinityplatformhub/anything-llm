## The three previously-surviving mutants, checked properly

**M4 — the fix found something I had not.** I reported that the Sidebar test only rendered
`NewWorkspaceButton`. Dev2's first attempt at covering `:166` rendered `<Sidebar />`, which
**still does not reach it** — the wrapper lives in `SidebarMobileHeader`, a different
export. The comment records that. There is also a real trap in the assertion:
`SettingsButton` renders a "Settings" cog outside `/settings/*` and a **"Home"** arrow
within it, so a query matching only `/settings/i` finds nothing on the home route and every
negative assertion passes for free. The helper queries both labels. That is two ways the
test could have been green-for-the-wrong-reason, and both are closed.

**M6 — asserted through a second reader, which is the only place the bug is visible.** The
test counts `fetchMyCapabilities` calls: first mount rejects and `can()` is false (failing
closed, correct), second mount must call again and get `true`. A cached rejection answers
the second reader from the first without asking. There is a companion test that a
*successful* fetch is still cached, so the fix cannot degrade into a request storm — and
M5 kills that one, which is the right cross-check.

**M3 — a source assertion, and I tested whether it is a tautology.** The DOM cannot
distinguish the two implementations: `useWorkspaceCapabilities` derives `can` from
`state.workspace?.capabilities`, so an invisible workspace already forces `can()` false and
both spellings hide the control. Dev4 established this for the picker; it holds here.

So the mutant is killed by `expect(source).toMatch(/visible && can\("workspace\.write"\)/)`.
A source-text assertion can be worthless, so I probed it: I changed the source to
`!loading && (visible && can("workspace.write"))` — **identical behaviour, different
spelling**. Result: `82 passed, exit 0`. The assertion did not fail.

That is worth stating precisely rather than as a verdict. The assertion is **not** a
tautology in the sense that matters — removing `visible` does fail it, which is the mutant
it was written for. But it is pinned to one spelling, so it is a text guard rather than a
behavioural one: an equivalent refactor passes, and a *differently*-equivalent refactor
(say `[visible, can(...)].every(Boolean)`) would fail it while breaking nothing. The
comment says as much ("Asserted on the source, so removing the check fails loudly instead
of silently becoming decorative"), and the accompanying DOM test documents the behaviour.
Given the hook genuinely makes the two indistinguishable today, I accept it — but it is a
maintenance cost, not a free guard, and if `useWorkspaceCapabilities` ever gains a state
where `visible` and `can()` diverge, the DOM test that becomes possible then should replace
this one rather than sit beside it.
