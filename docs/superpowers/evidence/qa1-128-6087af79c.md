## NIT-1 — the null-`grantPrincipal` guard is unpinned

`policyRepository.js`, `heldPermissionIds`:

```js
if (!grantPrincipal) return new Set();
```

M6 removes it and the suite stays **49/49**. Measured consequence, with an api-key-shaped actor whose creator has been deleted (`grantPrincipal: null`):

```
clean tree : {"threw":false,"canAssignAdmin":false}
M6 mutant  : {"threw":true,"message":"Cannot read properties of null (reading 'type')"}
```

So the guard is load-bearing — without it the call throws a TypeError rather than answering "holds nothing". Its comment states the intended behaviour ("A key whose creator has been deleted evaluates as nobody and holds nothing"), and PMO listed it as a probe item, but no test asserts it.

Direction matters here: a throw out of `heldPermissionIds` reaches `grantRole` / `canAssignLegacyRole` / `refuseGroupEscalation`, all of which are guards. Whether that throw is caught and turned into a refusal, or escapes as a 500, depends on the caller — so this is not automatically fail-closed the way the comment's intent is. One test closes it:

```js
expect(await canAssignLegacyRole({ actor: { ...keyActor, grantPrincipal: null }, targetRole: "admin" })).toBe(false);
```

Not a blocker: an orphaned key is not reachable through `resolveActor` today (a key with no creator row resolves to a null actor before reaching here), so the case is defensive. But it is defensive code with a stated contract and no witness, and the same class as the guards I raised on #115 and #122 — the difference being that this one is measurably not equivalent.
