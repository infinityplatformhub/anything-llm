## 2. Listing mask — gated on `user.manage`, both surfaces

```
reader (invite.read, NO user.manage) -> ["a***@example.com", ...]  realAddressInBody=false
super_admin (POSITIVE CONTROL)       -> ["a1@example.com", ...]    realAddressInBody=true
/v1/admin/invites (invite.read key)  -> ["a***@example.com", ...]  realAddressInBody=false
```

`whereWithUsers` masks **by default** and unmasks only when a caller passes
`unmaskEmail: true` (`models/invite.js:244`), which the session route sets from a
`user.manage` check (`endpoints/admin.js:276-283`). `/v1` omits the option entirely, so it
masks — fail-closed by construction rather than by remembering.

The positive control matters: without it, "masked" and "the list was empty" look identical.

```
ML (mask removed at the model) -> 3 failed
   including BOTH "a caller without user.manage sees…" AND
   "the /v1 listing never shows a full address" — two surfaces, two tests.
```

### The `[16,10]` I flagged mid-probe was mine, not the code's

I reported two different masked lengths and said it might disclose the local-part length.
It does not. `maskEmail` is `${value[0]}***${value.slice(at)}` — the local part always
collapses to exactly 1 + 3 characters, and the remaining variation is the **domain**, which
is kept verbatim by design and is not secret:

| input | mask | local len | domain |
|---|---|---|---|
| `a@x.com` | `a***@x.com` | 1 | x.com |
| `ab@x.com` | `a***@x.com` | 2 | x.com |
| `alice@example.com` | `a***@example.com` | 5 | example.com |
| `averylonglocalpart@example.com` | `a***@example.com` | 18 | example.com |

A 1-character and an 18-character local part produce byte-identical masks on the same
domain. Dev3/TL-1's fixed-width claim is correct; my `[16,10]` was two different domains.

## 4. `mailed` distinguishes three outcomes

```
copy-link invite  -> mailed=false  error=null
mailed-but-FAILED -> mailed=false  invite=true  error="The invite was created but the email could not be sent…"
```

A failed send is never `mailed:true`, and it is separable from a copy-link invite by the
error field rather than by the flag alone.

### `smtp_verified_hash` is writable — and that is not a hole

`smtp_verified_hash` is in `supportedFields`, so `POST /admin/system-preferences` can write
it. I chased this as a possible forgery of the "these settings were proven to work" marker.
It is not forgeable:

```
POST /admin/system-preferences {smtp_verified_hash: <attacker guess>} -> 200, row holds the guess
isVerified() with that guess                                          -> false
POST /mailer/settings afterwards                                      -> 409 "Send a test message…"
```

`configHash` is HMAC-SHA256 keyed on `SIG_KEY` (`mailerSettings.js:58-73`), so a caller
without the server secret cannot produce a value that verifies. Writing garbage there only
*invalidates* the proof — it fails closed. My earlier in-process "attack" computed the hash
with `SIG_KEY` in hand, which is not a position an HTTP caller occupies.

## Method note — a `yarn install` silently invalidated my first mutation round

My first run of MJ/MK/ML each reported ~30 failures, and re-checking the baseline on a clean
tree showed 90/119 rather than 119/119. Cause: the `yarn install` I ran when moving the
worktree to this SHA overwrote `node_modules/@prisma/client`, so the runtime client predated
the `invites.email` column while `schema.prisma` and `.prisma/client` both had it — every
suite touching a mailed invite died in `prisma.invites.create` with
`Unknown argument 'email'`. Re-running `prisma generate` restored 119/119, and all three
mutations were re-run against that clean baseline; only those results appear above.

Same lesson as the deleted-symlink incident on `35c91ab0`, in a new costume: **a harness
that cannot run looks exactly like a harness where everything fails** — and a broad,
uniform failure set is the tell, not the finding.
