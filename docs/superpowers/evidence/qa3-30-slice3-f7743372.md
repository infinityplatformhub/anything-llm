## S-25 — a count must not exceed the actor's scope

| id | scenario | result |
|---|---|---|
| A1 | 51 workspaces in scope | throws `CardinalityScopeTooLargeError`, and **`countFor` is called zero times** |
| A2 | exactly 50 | served, `vectorCount = 100` |
| A3 | key scoped to workspaces 7 and 9 (counts 5 and 7) | **12**, not the instance's 999 |
| A4 | org-wide | 999 — the instance total, correctly |
| A5 | `matchNone` | `0`, and the vector store is **never touched** |
| A6 | `aclFilter` absent | both helpers throw rather than counting everything |

A1 is the amplification cap doing what it claims: the refusal happens **before**
any per-namespace query, so a wide scope cannot fan out into 51 store round trips
on its way to being refused.

A3 is #67 restated for counts — a bound key learns its own total and nothing
about the rest of the instance.

## S-25 — absent and forbidden are the same answer, at the same cost

| scenario | returns | slug lookups | store touched |
|---|---|---|---|
| workspace does not exist | `null` | 1 | no |
| workspace exists, not in scope | `null` | 1 | no |
| `matchNone` | `null` | **0** | no |
| in scope (control) | `42` | 1 | yes |

The first two rows are the finding: identical return, identical number of
lookups, and neither reaches the vector store. That closes the timing channel the
module's own rule 1 names — a refusal that ran a store query would be
distinguishable from a not-found that did not, however identical the bodies.

`matchNone` short-circuits before the slug lookup, which is stricter still and
costs nothing to have.

## One response shape for every outcome

```
empty  -> {"results":[]}
no-arg -> {"results":[]}
```

Byte-identical, and no `message` key in any branch. The old route returned
`{results: [], message: "No embeddings found for this workspace."}` when the
namespace count was zero, while an ACL-filtered search that matched nothing
returned `{results: []}` — so a caller could tell "there is content here you may
not read" from "there is nothing here". Asserted on the serialized body, not on
parsed fields, so a stray key cannot slip through.

## S-22 — citations rehydrated from history are re-authorized

Driven with the exact shape `authorizedSimilaritySearch` builds
(`retrievalFilter.js:125` wraps each result as `{metadata: {...}}`), through each
provider's own `curateSources`, then through `fillSourceWindow`:

| id | check | result |
|---|---|---|
| F1 | providers discovered from the directory | **10**: astra, chroma, chromacloud, lance, milvus, pgvector, pinecone, qdrant, weaviate, zilliz |
| F2 | `orgId`/`workspaceId`/`docId` survive `curateSources` | all 10 keep all three |
| F3 | a foreign citation is refused; my own survives | 0 leaks, 0 own-rows lost, per provider |
| F4 | mutation: one provider rewritten to pick fields explicitly | its rows become unprovable and are **all** denied — including the caller's own |

F4 is the failure mode Dev4's comment predicts, made real: replacing qdrant's
`{...metadata}` spread with an explicit `{id, text, title, score}` pick strips the
ACL fields, and `fillSourceWindow` then denies every row from that provider rather
than serving them unchecked. Fails closed, loudly enough to notice.

Two more, on `fillSourceWindow` directly: a citation with no ACL fields at all
(stored before slice 1a) is denied; calling it without an `aclFilter` throws
`AuthorizationContractError` rather than re-serving everything.

## Note on my own probe

My first attempt asserted against `curateSources` output built from a flat row
and reported five providers "dropping ACL fields". That was my fixture, not the
code: pinecone, chroma, chromacloud, milvus and zilliz read `source.metadata` and

nests. Re-run with the real shape, all ten keep all three fields. Recorded because
a reader comparing notes should know which of the two runs was wrong.
