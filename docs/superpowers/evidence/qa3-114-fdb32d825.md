## Field counts do not match the pre-read, and tests must not pin them

TL-2's pre-read said 92 fields. I measure **135** authenticated and **159** pre-user on my
box. Both are correct: `currentSettings()` emits fields conditional on which providers are
configured, and I planted seven environment variables, so more appear. The pre-user body
being *larger* than the authenticated one looks contradictory but is not — they are taken
in different instance states (`isConfirmedSingleUser` differs), and the pre-user branch is
`{...settings}` with values emptied rather than keys removed.

The consequence for the suite: **no test may hardcode a count**. Mine asserts `>= 92` and
compares key lists; Dev1's compares against `PUBLIC_SETTING_FIELDS` and the drift pattern.
Same lesson as #84 — derive, do not count.

## `callerHasSession` — running the middleware rather than reimplementing it

The helper invokes the real `validatedRequest` against a response stand-in that swallows
what it writes, so a refusal is read as "no session, narrow the body" rather than sent. I
probed the failure path directly: a malformed bearer token returns 200 with the six-field
body (R-bad), not a 500 and not the wide body. The `.catch(() => finish(false))` is what
makes that true, and it is the right default — an unparseable token is not a session.

The alternative, a second local "is this caller authenticated" check, is what the comment
declines to write, and I agree with the reasoning: single-user passthrough, the encrypted
`p` format and the multi-user branches would all need duplicating, and the two copies would
drift the way this codebase has already seen elsewhere.

## Residual

- The pre-user branch returns **159 keys** with endpoints emptied. That is still a large
  surface of provider names, model preferences and engine choices to an unauthenticated
  caller — `EmbeddingModelPref`, `OpenAiModelPref`, `AgentSerpApiEngine` and so on. It is
  deliberate (onboarding mounts 37 components that read those keys) and the window closes
  the moment a user exists, but it is worth stating plainly: on a fresh install, before
  anyone signs up, the instance still tells an anonymous caller which providers it is
  configured for. Narrowing that further is a separate question about onboarding's data
  needs, not a defect in this fix.
- `SimpleSSONoLoginRedirect` is `null` and `SSOProviders` is `[]` in the public six. Any
  future assertion of "all six are booleans" would be wrong; they are three shapes.
