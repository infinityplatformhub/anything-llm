## `/api/metrics` is unauthenticated, and the allowlist is the only thing in front

| id | `IP_ALLOWLIST` | result |
|---|---|---|
| M1 | empty (the default) | **200**, `text/plain; version=0.0.4`, body contains `# HELP` — no credential presented |
| M2 | `203.0.113.0/24`, caller is loopback | **403** `{"error":"Access denied."}`, no `# HELP` in the body |
| M3 | `127.0.0.1,::1` | **200** |
| M4 | `not-an-ip-at-all` | **403** — a malformed allowlist fails closed rather than falling back to open |

M1 is the exposure the route's own comment describes, confirmed rather than
taken on trust: on a default install this endpoint answers anyone who can reach
the port. M4 is the one worth calling out — `parsedAllowlist()` returning `null`
on a parse failure is treated as "deny", not as "no allowlist configured", so a
typo in the operator's configuration does not silently open the endpoint.

## The doctor warns about exactly that combination

```
[WARN] config.metrics_exposure — IP_ALLOWLIST is empty, which allows every
       address. /api/metrics is unauthenticated, so anything that can reach this
       port can read the instance's counts and error rates.
Ready to start. 1 warning(s) — the install works as it is.       exit 0
```

With `IP_ALLOWLIST=10.0.0.0/8` it reads
`[PASS] … reachable only from the addresses it names.`

Warn, not block, and exit 0 — correct: an instance on a private network is fine
as it is, and refusing to boot over a scrape endpoint would be worse than the
exposure it prevents.

## The label vocabulary is closed on both halves

The risk in a metrics endpoint is the labels, and an allowed label *name* with a
free-text *value* is the same leak wearing a different hat. Both are refused:

| input | result |
|---|---|
| `{workspace: "acme-legal-due-diligence"}` | throws — `label "workspace" is not allowed` |
| `{provider: "acme-legal-due-diligence"}` | throws — `label value … is not allowed for "provider"` |
| `{provider: "priya@example.com"}` | throws |
| `{provider: "https://llm.acme.internal:8080"}` | throws |
| `{outcome: "failed: /Users/priya/deal.pdf"}` | throws |
| `{kind: "acme-q3"}` | throws |
| `observe("chats_by_workspace", …)` | throws — `unknown metric` |
| **control**: `{provider: "openai"}`, `{outcome: "success"}`, `{kind: "chat", outcome: "failure"}` | accepted |

The self-hosted-URL row matters as much as the workspace-name row: an operator's
internal endpoint is as identifying as a customer's deal name, and the module's
comment says so explicitly.

M6: every counter's declared `labelNames` — across `chats_total`,
`embeddings_total`, `documents_total`, `auth_attempts_total`,
`operations_total` — is inside `ALLOWED_LABEL_NAMES`. Checked from the registry
rather than from a list in the test, so a counter added later with a new label
fails here.

M7: the rendered body (8030 bytes, after incrementing two counters) contains none
of `acme`, `priya`, `@`, `workspace=`, `user=`, `email`, `/Users/`, `http://`,
`https://`. The only labelled lines are prom-client's process defaults
(`nodejs_active_resources{type="TCPServerWrap"}` and similar).

## Note

`observe()` throwing is the right call for a vocabulary violation, but it means a
call site that gets a label wrong takes down the request it is instrumenting, not
just the metric. Every call site in this SHA passes literals, so nothing can
throw today. If a future one ever computes a label from data, that becomes a
liveness question rather than a privacy one — worth a residual line, not a change
here.
