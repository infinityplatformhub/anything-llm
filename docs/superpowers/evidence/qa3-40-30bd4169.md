## The four refusals refuse, and refuse in the API's shape

Driven through the real mounted router:

```
POST   /api/system/update-password   -> 401 application/json {"error":"No auth token found."}
POST   /api/system/generate-api-key  -> 401 application/json {"error":"No auth token found."}
DELETE /api/system/api-key/999999    -> 401 application/json {"error":"No auth token found."}
POST   /api/telegram/connect         -> 401 application/json {"error":"No auth token found."}
```

The runtime change is a body where there was none — status and semantics are
unchanged, and no caller can have depended on `text/plain` from a 401 it was
already treating as a failure. The frontend's fetch wrappers parse JSON on the
error path, so a JSON body is the shape they already expect.

Two `sendStatus(401|403)` sites remain in `system.js` and are correctly left
alone: `:192` (suspended user, a GET) and `:1159` (`GET /system/api-keys`).
Neither is a mutating route, so neither is in `SINGLE_USER_ONLY_ROUTES` and
neither is what this sweep is about.

Neither mutation makes the sweep pass vacuously: an empty `WeakSet` means

and the assertion fails loudly. That is the right direction — the failure mode of
this evidence mechanism is over-reporting, not under-reporting.

Both registries are `Symbol.for`-keyed on `globalThis` and installed with

is test evidence rather than a security boundary. Worth repeating here because
the distinction is easy to lose: nothing at runtime consults these sets to decide
access; they exist so a test can tell a real gate from a function that merely
looks like one.
