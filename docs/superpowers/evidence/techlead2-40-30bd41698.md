## (ค) The four `sendStatus(401)` → JSON changes

Measured what actually differs on the wire:

```
sendStatus(401):  401 | text/plain; charset=utf-8       | "Unauthorized"
status+json:      401 | application/json; charset=utf-8 | {"error":"Single-user mode required."}
```

**Refusal semantics are unchanged**: same status, same set of callers refused, no branch moved.
What changes is content type and body, and that is exactly what the shape-B suite now needs —
it treats a non-JSON response as "did not reach the route", which is how the SPA-fallback html
was being mistaken for a real answer.

The new guard is load-bearing, not decorative. I reverted one route to `sendStatus(401)` and
the suite caught it by content type:

```
✕ no single-user-only route answers 2xx to an impersonated session
✕ no single-user-only route answers 2xx to an ORDINARY session
    "POST /system/update-password → 401 text/plain; charset=utf-8"
```

So the four routes changed are precisely the four the suite exercises, and the suite fails if
any of them regresses. That is the right scope: the change is not a stylistic sweep, it is the
minimum that makes the assertion possible.

### Observation — the same pattern remains elsewhere, correctly out of scope

`sendStatus(401)` still appears at `endpoints/system.js:1159` (`GET /system/api-keys`) and at

those sites will need the same treatment — and the reason will be the same one, so the
consistency is worth reaching eventually. Not this change's job.

## NIT-1 — the per-layer allowlist, and it is attackable

My NIT was that a signature match could let a second layer inherit another route's exemption.
The fix filters *all* matching layers and asserts `toHaveLength(1)`, with the comment *"one
signature exempts exactly one mounted layer; collisions never inherit another route's
reason."*

I attacked it directly — mounted a second, ungated `POST /system/update-password` (an
allowlisted signature) on `apiRouter`:

```
✕ the sweep actually mounted the router (guards the guard)
✕ every mounted mutating route has identity-verified authorization
```

Two independent failures: the route count moves (309 → 310) and the gate check refuses the
duplicate. So an ungated route hidden behind an existing exemption is caught twice over.

The change also fixes a latent narrowing I had not flagged: the old code read
`Object.keys(layer.route.methods)[0]`, so a layer registered for more than one method was
compared on its first method only. The new version checks every method on the layer.
