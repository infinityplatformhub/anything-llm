## F1 CLOSED — two consents, and the old spelling maps to the safe half

`transportOptions()` is now public and the decision is made in one place. Measured
across all four combinations:

```
allowInsecure: true (old spelling)      -> tls = undefined     <- cert still validated
allowInsecureTransport: true            -> tls = undefined
secure + allowInsecureTransport         -> tls = undefined     <- the exact case that leaked
allowUntrustedCertificate: true         -> tls = {rejectUnauthorized:false}
```

The compatibility read of `allowInsecure` feeds **only** the transport half, so an
existing configuration carrying the old flag silently gets *safer* rather than
keeping the old behaviour — the right direction for a flag whose old meaning was the
bug. Three tests pin all three positions including the default.

Making `transportOptions()` public rather than asserting through a staged untrusted
peer is the right call: the decision is the property, and a test needing a CA to
observe it is a test nobody maintains.

## F2 CLOSED — keyed by `notificationId`, and the failure path stays retryable

```
same notificationId twice   -> relay messages: 1  | same deliveryId: true
status(deliveryId) after    -> "queued"
4xx failure, then retry     -> both throw NotificationUnavailableError
                               DATA attempts at relay: 2      <- retry really re-sent
```

The second line is the one that matters and it is what I would have got wrong:
memoising failures would turn one transient outage into permanent silence. Only a
successful send is remembered, and the suite asserts it across two fixtures (fail
then succeed, one message lands).

`status()` now scans values for a `deliveryId` rather than re-keying the map — the
comment says why, and the map is bounded so the scan is bounded. Fine at this size.

The `evt-1:alice` / `evt-1:bob` test is a better idea than my finding: it pins that
one event to two recipients is two messages, so a future `notificationId` derived
from the event alone collapses two invitations into one and goes red. That is the
failure mode on the other side of the fix.

## F3 CLOSED — the field is gone, not stubbed

`"retryAfterMs" in error` → `false` on a 4xx. The replacement comment states the
reason and names where the field would belong (an HTTP channel reading

## OBS-1 — F1 split the driver's consent in two; the settings that feed it still carry one

`SETTING_KEYS` is `[smtp_host, smtp_port, smtp_secure, smtp_allow_insecure,
smtp_username, smtp_from_address, smtp_from_name]` — a single `smtp_allow_insecure`,
with no row for the certificate consent. So whatever maps settings onto the driver in
the config lane must decide what `smtp_allow_insecure` means, and the tempting answer
— pass it to both — reassembles the coupling F1 just removed, one layer up.

Not a defect in this SHA: nothing maps settings to a driver yet. But it is the
seam where the fix can be undone silently, so it should be ruled on before the
config lane writes that mapping: add `smtp_allow_untrusted_cert` to `SETTING_KEYS`
(it is connection-determining, so it belongs in the hash regardless), and let
`smtp_allow_insecure` feed only `allowInsecureTransport`.

## OBS-2 — `actorKey` buckets by raw bearer token, so a rotating session token gets a fresh budget

`actorKey` is `digest("actor:" + bearer)`. For an API key that is exactly right — the
key is the identity. For a **session JWT** it is not: the token is the credential, and
a new login (or any re-issue) produces a different string and therefore a fresh
bucket. An admin session cannot rotate a token quickly enough to matter, so this is
not an exploitable hole; the effect is that the limiter meters *tokens*, not *actors*,
and the name says otherwise.

The comment gives the correct reason for not using `response.locals.actor` (the
limiter runs before `requirePermission`). A middle path exists: decode the JWT's `id`
without verifying it, fall back to the raw bearer when that fails. Unverified is fine
here — an attacker forging a *different* id only moves themselves into someone else's
bucket, which is worse for them.

Worth a line either way, since the reason the bucket exists is "one compromised key
must not mail a customer list", and that argument is about a key.
