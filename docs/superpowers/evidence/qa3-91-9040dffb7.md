## The credentialClear premise guard (item 6) — it does assert the substance

The status changed `200 → 500` in that test, so the question was whether the refusal text
and the surviving row are still really asserted or whether the status now carries the test.

My first attempt at this was a bad probe: I deleted the assertions from the test file and
the suite stayed at 27/27 — which proves nothing, since removing an assertion can never
fail a test. Redone against the code:

| id | mutation | result |
|---|---|---|
| P6c | `isNotEmpty` message no longer contains "empty" | **1 failed** — `Expected pattern: /empty/i, Received string: "Value is not acceptable"` |
| P6d | `isNotEmpty` disabled | **1 failed** — falls through to `"OpenAI Key must start with sk-"` |
| P6e | `isNotEmpty` **and** `validOpenAIKey` both disabled | **2 failed** — status `Expected: 500 Received: 200`, and `force does not bypass it either` |

So all three claims are load-bearing: the refusal text, the fact that a refusal happens at
all, and (P6e, where the write actually goes through) the status. The row assertion is the
one I could not isolate — with both validators off the request succeeds and the test fails
on status first — but the write path is the same one M2 exercises, and M2 proves the row
read is real.
