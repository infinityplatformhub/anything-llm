## 1. O3 — the migration does not touch existing rows

Tested the way the risk actually arises: applied every migration **before** slot 093000,
seeded invites on the old schema, then applied the rest.

```
before: invites(claimedBy, code, createdAt, createdBy, id, lastUpdatedAt, status, workspaceIds)
seeded: LEGACY-PENDING-CODE (pending), LEGACY-CLAIMED-CODE (claimed)
after 093000 + the rest:
  LEGACY-CLAIMED-CODE | claimed  | email NULL | expiresAt NULL
  LEGACY-PENDING-CODE | disabled | email NULL | expiresAt NULL
```

`expiresAt` is **NULL on both** — no column DEFAULT, so no legacy invite acquired a
deploy-dated expiry. This is the failure that would have been invisible in CI, where every
database is fresh.

`LEGACY-PENDING-CODE` reads `disabled` because of #71's `20260902110000` migration, which
revokes all pending invites. That is pre-existing and unrelated to #80.

A separately seeded post-migration row with `expiresAt` NULL still resolves through
`Invite.get` (`FOUND status=pending`), so "never expires" survives as a live state.

## 2. O1 — the redemption oracle is closed

Four states driven over HTTP, compared as **raw text and `content-length`**:

| state | status | len | body |
|---|---|---|---|
| unknown code | 200 | 59 | `{"success":false,"error":"Invite not found or is invalid."}` |
| expired | 200 | 59 | identical |
| already claimed | 200 | 59 | identical |
| disabled | 200 | 59 | identical |

**Byte-identical across all four.**

The oracle I reported in pre-read is closed:

```
dup-username on VALID   code -> 200 len=59 {"success":false,"error":"Invite not found or is invalid."}
dup-username on UNKNOWN code -> 200 len=59 {"success":false,"error":"Invite not found or is invalid."}
```

Previously the first would have returned `User.create`'s own message, confirming a live
invite. And caller-fixable input still gets a useful message that does **not** depend on the
code:

```
weak password, unknown code -> {"success":false,"error":"password should be at least 8 characters long"}
weak password, VALID   code -> identical
```

`GET /invite/:code` gives the same non-disclosing answer for all four states.

## 3. O2 — expiry in `Invite.get`; `deactivate` exempt

- `Invite.get({code: expired})` → `null`
- `Invite.deactivate(expired)` → `{success:true}` — per ruling, an admin may tidy an expired row
- `Invite.get` on a NULL-expiry row → found

## 4. O4 — pairing and TTL (behaviour correct; see NIT-1 for coverage)

| input | result |
|---|---|
| `email` present | `expiresAt` set, **~7 days** |
| no `email` | `expiresAt` NULL — copy-link unchanged |
| `email` + explicit `expiresAt: null` | **refused**: "An emailed invite must have an expiry." |
| `email: "   "` (whitespace) | normalised to NULL → treated as copy-link, no expiry |
| `email` + explicit 1h | ~60 minutes — an explicit value wins over the default |

## 5. TL-2 OBS-1 — the claim race

`markClaimed` is a conditional `updateMany` on `status: "pending"` plus a non-expired
predicate, with `count === 1` as the answer.

```
two concurrent markClaimed on one invite -> A=true B=false   exactly one: true
final status=claimed claimedBy=9001
markClaimed(expired) -> {success:false, error:"Invite not found or is invalid."}
```

The route consumes the result and returns the shared refusal when the claim fails, so a
racer that loses after `User.create` is not told it succeeded.

## NIT-1 (non-blocking) — the pairing rule is unconstrained

M4 replaces `if (normalizedEmail && !expiry)` with `if (false)` and the suite stays green at
10/10.

Not an equivalent mutant — measured under the mutation:

```
Invite.create({ email: "leak@example.com", expiresAt: null })
  -> CREATED  expiresAt=null  email=leak@example.com
```

That is exactly the state the rule exists to prevent, and the state the migration comment
calls out by name: *"A link sent to an inbox and valid forever is a bearer credential sitting
in mail history."* The rule is correct at this SHA; nothing would notice if it were removed.

The gap is reachability, not correctness. No route passes `email` to `Invite.create` yet —
route wiring is a later stage — so the only caller that can exercise the rule today is a test.
The suite is HTTP-driven (`inviteExpiryHttp.test.js`), and the rule cannot be reached over
HTTP, so it went untested.

Smallest fix is a model-level case alongside the HTTP ones:

```js
await expect(
  Invite.create({ createdByUserId: 1, workspaceIds: [], email: "x@example.com", expiresAt: null })
).resolves.toMatchObject({ invite: null });
```

Worth adding before the stage that wires `email` into the routes, since that is the point at
which an unnoticed regression becomes reachable by an admin.
