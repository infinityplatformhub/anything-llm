## The forgery guard — measured on all four shapes

```
raw {status:"complete"}                              REFUSED
Symbol reconstructed with Symbol("...same text")     REFUSED
object with NO status field at all                   accepted, complete:false, deactivate:0
Symbol COPIED off a real completedEnumeration()      accepted, complete:true, deactivate:[u17,u18,u19]
```

The first three are right. The fourth is the brand's real boundary and it is the correct one: `Symbol()` is unforgeable by description, so the only way to hold it is to have been given a genuine completed value. That is a stronger property than a boolean field and matches what the module's comment claims.

## TL-1's finding — laundering a failed run — is real, and is not this module's to fix

```
failedEnumeration({reason:"page 37 died", principals:[…17 of 20…]})
  → completedEnumeration({principals: failed.principals, groups: failed.groups})
  → diffDirectory  ⇒ complete:true, deactivate:[u17,u18,u19]
```

`completedEnumeration()` takes raw arrays and asserts completeness over whatever it is handed, so a caller that unwraps a failed run and re-wraps its data gets deactivations from an incomplete snapshot. The brand is doing its job — it certifies "this came from `completedEnumeration`", not "the enumeration finished" — and no type can stop a caller that deliberately restates the claim.

The right containment is at the call site in slice 2 (only the enumerator constructs these; a failed run's arrays never travel separately), and the existing test `a failed enumeration cannot even be constructed as a complete one` covers the accidental version. Recording it as a residual with the wording *"the brand certifies provenance, not truthfulness — slice 2 must not unwrap and re-wrap"* is enough; making `completedEnumeration` private to the driver would be stronger and is slice 2's call.

Passed through directly, a failed run behaves correctly: `complete:false, deactivate:0, removeMembership:0`.
