## RULING: **(1)** — un-suspend **ไม่** ล้าง `revokedAt` · ผู้ใช้ต้อง mint key ใหม่

### ข้อเท็จจริงที่ตัดสินให้ — **(2) แก้ปัญหาที่ไม่มีอยู่**

ผมยิงหาผู้เขียน `revokedAt` ทั้งฐานโค้ด:

```
models/user.js:37          revokeCredentialsFor (สวีปของ #136)   <- ผู้เขียนเพียงรายเดียว
models/apiKeys.js:91       อ่าน (validate)
actorResolver.js:92        อ่าน
validApiKey.js:153         อ่าน (ส่งต่อลง context)
```

**ไม่มี "การเพิกถอนโดยมนุษย์" ที่เขียน `revokedAt` เลย** · เส้นทางที่ admin ใช้จริงคือ
`DELETE /admin/delete-api-key/:id` → `ApiKey.delete` → `prisma.api_keys.deleteMany`
(`models/apiKeys.js:103`) — **มันลบแถวทิ้ง ไม่ได้ stamp**

**M5 conflict ที่ (2) ตั้งใจแก้ จึงไม่มีอยู่ในโค้ดวันนี้** · แถวที่มี `revokedAt` ไม่ null
มีทางเดียวที่มาได้ คือสวีปของ #136 · การเพิ่ม tag เพื่อแยกสองแหล่งที่มา ในเมื่อมีแหล่งเดียว
คือการเพิ่มคอลัมน์/ค่าที่ไม่มีอะไรอ่านต่างกัน — **หนี้ที่จ่ายก่อนถึงกำหนด**

### เหตุผลเชิง audit — ทำไม (1) ถูกแม้ในวันที่มีการเพิกถอนโดยมนุษย์

`revokedAt` เป็น **timestamp ไม่ใช่ boolean** · มันตอบคำถาม *"credential นี้หยุดทำงาน
เมื่อไร"* ซึ่งเป็นข้อเท็จจริงทางประวัติศาสตร์ · การล้างมันคือการเขียนทับคำตอบว่า
"ไม่เคยหยุด" ซึ่ง **เป็นเท็จ** — key นั้นหยุดทำงานจริงในช่วงที่ถูกระงับ

ระหว่างที่ถูกระงับ credential นั้นอาจถูกใช้พยายามเข้าถึง ถูกส่งต่อ หรือถูกเก็บไว้โดยคนที่
ไม่ควรมี · **การคืนชีพให้อัตโนมัติแปลว่าการ offboard เป็นเรื่องชั่วคราวโดยที่ไม่มีใคร
ตัดสินใจว่าจะให้ชั่วคราว** · การ mint ใหม่ใช้เวลาสิบวินาที และมันบันทึกว่ามีคนตัดสินใจ

**ทิศทางความปลอดภัยไม่สมมาตร**: (1) พลาด = ผู้ใช้ต้องสร้าง key ใหม่ (น่ารำคาญ มองเห็นได้
แก้เองได้) · (2) พลาด = credential ที่เคยถูกเพิกถอนกลับมาทำงานเงียบ ๆ (มองไม่เห็น
และไม่มีใครรู้ว่ามันกลับมา)

### สิ่งที่ต้องเขียนไว้ให้ตรง

JSDoc ของ `revokeCredentialsFor` ต้องบอกว่า **การเพิกถอนนี้ถาวร** และ un-suspend
ไม่คืนสภาพ key · ตอนนี้เขียนแค่ว่า "already-revoked keys are left alone" ซึ่งอธิบาย
filter แต่ไม่ได้ประกาศนโยบาย

**ถ้าวันหนึ่งมีการเพิกถอนโดยมนุษย์ที่ stamp `revokedAt`** (แทนที่จะลบแถว) คำถามเรื่อง
tag จะมีความหมายขึ้นมา · **ตอนนั้นค่อยตัดสิน** และ (1) ไม่ได้ขวาง — มันคือค่าตั้งต้นที่
ปลอดภัยและไม่ต้องแก้ถ้ายังไม่มีใครขอ

## D1 — ยืนยัน: `createdBy = null` → `SINGLE_USER_ACTOR` **ต้องไม่ถูกแตะ**

ผม prototype (a) เองแล้ววัด control นี้ตอนออก ruling ก่อนหน้า — **ผ่าน**

โครงที่ถูกคือใส่การเช็คไว้ **ในสาขา `creatorId !== null` เท่านั้น**:

```js
if (creatorId !== null) {
  const owner = await db.users.findUnique({ where: { id: Number(creatorId) }, select: { suspended: true } });
  if (!owner || owner.suspended) return null;
  return { type: "user", id: String(creatorId) };
}
// null branch ไม่เปลี่ยน — isConfirmedSingleUser แล้วคืน SINGLE_USER_ACTOR
```

**เหตุผลที่ข้อนี้สำคัญกว่าที่ดู**: คอมเมนต์ที่ `:236-245` เขียนไว้ตรง ๆ ว่า
deployment แบบ single-user **ทุก key มี `createdBy` เป็น null** · ถ้า (a) เผลอปฏิเสธ
สาขานั้น `/v1` ตายทั้งดีพลอยเมนต์ ในกลุ่มผู้ใช้ที่วินิจฉัยเองได้ยากที่สุด ·
**เป็น fixture ที่ต้องมีในชุด ไม่ใช่ข้อสังเกต**

ปัจจุบัน · ล้างมันคือการเขียนทับความจริงว่า credential ไม่เคยหยุด และ (2) แก้ M5 conflict
