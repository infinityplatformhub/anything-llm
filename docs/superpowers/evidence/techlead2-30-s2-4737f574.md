## BLOCKER-1 — closed, both halves, measured

The fix is two independent checks: a positive workspace-scope gate before the query, and a
per-row org check on `document.orgId` joined via `include`. I drove `pinnedDocs` directly
against a real database with three workspaces and a genuinely cross-org document:

```
scoped-to-A asks A      : ["ORG1 WORKSPACE A DOC"]     <- own scope still works
scoped-to-A asks B      : []                           <- the leak, closed
orgWide org1 asks B     : ["ORG1 WORKSPACE B DOC"]     <- orgWide crosses workspaces
orgWide org1 asks OTHER : []                           <- but NOT orgs
scoped org1 -> WOTHER   : []
```

Line 2 is the blocker from round 2, now returning nothing. Line 3 confirms the fix is a
scope check rather than a blanket refusal — an org-wide service principal still reads
across workspaces, which was the thing most likely to break while closing this.

**Line 4 is the check I most wanted to see, and it passes.** `orgWide: true` skips the
workspace gate by design, so if the org check had been placed inside that branch — the
natural way to write it — an org-wide principal would have read another tenant's pinned
documents, and the fix would have traded a workspace leak for a worse org leak. It is
placed on the row instead, so it applies in both branches. The code says so explicitly:
*"orgWide is 'every workspace in YOUR org', never every org — so this check applies in both
branches above."*

I mutated exactly that, since a correct-by-comment placement is worth nothing without a
test holding it:

| mutation | result |
|---|---|
| workspace-scope gate disabled (`if (false)`) | **3 failed** / 22 |
| org-tenancy check removed | **1 failed** / 22 |
| org check made `orgWide`-conditional (the over-correction) | **1 failed** / 22 |
| scope `has()` check short-circuited | **3 failed** / 22 |
| embed `actorRef` removed (round-2 regression) | **1 failed** / 22 |

Both layers are load-bearing and are held **separately** — that was my own added check:
one test covering both would have let either half rot. The over-correction mutation (M3) is
the one that matters most, and it fails.

A row whose joined `document.orgId` is null counts as unprovable rather than allowed,
sharing the counter and the flag with the missing-`documentId` case. Verified with the flag
set on a cross-org workspace:

```
FLAG orgWide asks OTHER : ["NULL DOCID DOC"]
```

Only the unprovable row comes back; the org-2 labelled document stays excluded even with
the escape hatch on. Absence of evidence excused, evidence of denial not — the same rule as
every other path in this issue.

## The HTTP test is real, and its positive control is real

This was my second added check: an absence-assertion suite passes just as well when the
handler crashes before producing anything, so "not.toContain" proves nothing until
something is known to reach the wire. I captured the actual response body of the positive
control:

```
data: {"uuid":"test","type":"textResponseChunk",
       "textResponse":"[\"PINNED DOC OF A\"]",
       "sources":[{"text":"PINNED DOC OF A...continued on in source document...",
                   "token_count_estimate":10,"title":"a-doc"}],
       "close":false,"error":false}
data: {"uuid":"…","type":"finalizeResponseStream","close":true,…}
```

The document is genuinely on the wire, in both `textResponse` and `sources`, through a real
supertest request with a real JWT. So the two "must not contain" assertions on workspace B
are being made against a request shape that demonstrably *can* carry a pinned document.

Three further things this suite gets right, worth naming because each is a trap I have seen
elsewhere in this issue:

- It asserts `response.status === 200` on the cross-workspace request. If a future change
  starts 403ing there, the leak assertion would pass for a reason unrelated to the ACL —
  pinning the 200 stops that silently.
- The third test parses `sources` out of the SSE stream separately from the prompt text.
  `sources` is what the UI renders; a fix that filtered `contextTexts` alone would still
  show the title and first 1000 characters of B's document.
- `streamingEnabled` is stubbed with a comment saying the suite aborted before retrieval
  without it, and that the positive control is what exposed that. That is the failure mode
  being caught by the mechanism designed to catch it.

The vector store is stubbed empty on purpose, so anything appearing in the response got
there through pinned injection and nothing else. Its `queryAuthorized` throws if called
without an `aclFilter`, which keeps the stub from becoming a hole.

## Embed prefetch — closed, and both halves are asserted

`actorRef` now threads `embed.js` → `resolveProviderConnector` → `gatherRoutingContext` →
`authorizedPinnedDocs`. `embedRouterPrefetchActor.test.js` asserts the seam (the ref

One honest limitation, and the test states it itself rather than hiding it:
`resolveLLMConnectorForEmbed` is not exported (`embed.js:354` exports only

The fallback is explicit and commented — *"a test that quietly proves nothing is worse than

call site with the router enabled; the seam test covers the behaviour, the source test
covers the wiring, and neither covers them composed. Not worth blocking on, since the leak
direction here is fail-closed.

## Two notes, neither blocking

**NOTE-1 — the org check reads `row.document.orgId`, which is now a required join.**
`pinnedDocuments()` supplies it via `include: { document: { select: { orgId: true } } }`.
If a future caller reaches `pinnedDocs` with rows fetched some other way, `row.document`
is undefined, `rowOrgId` is undefined, and the row is treated as *unprovable* — excluded by
default, admitted when the flag is set. Fail-closed in the default state, which is right,
but on a flagged deployment a missing join silently becomes "serve it". The two are one
function apart today; a comment on `pinnedDocuments` saying the include is load-bearing for
`pinnedDocs`, not a convenience, would keep them together.

**NOTE-2 — the workspace-scope refusal is logged, the org refusal is not.**
An out-of-scope workspace logs a clear reason. A row dropped for org mismatch returns
`false` silently. That asymmetry is defensible — a per-row log on a hot path is noise — but
an operator debugging "my pinned documents vanished" after a tenant migration gets a signal
in one case and silence in the other. A single count at the end, like `unprovable` already
does, would close it cheaply.
