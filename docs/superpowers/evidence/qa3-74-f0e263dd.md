## Ruling 1 — a `VECTOR_DB` spelling the app will not match now fails

The disagreement QA-3 reported is closed, and closed in the direction that says
what went wrong rather than what is missing.

| id | `VECTOR_DB` | result |
|---|---|---|
| C1 | `PGVECTOR` | **FAIL**, exit 1 |
| C2 | `" pgvector "` | **FAIL**, exit 1 |
| C3 | `pgvector` | PASS — `VECTOR_DB is pgvector.` |
| C4 | `lancedb` | PASS, and `vector` is still not demanded |
| C5 | unset | PASS — `VECTOR_DB is not set; the default vector store is LanceDB.` |

The failing message names the actual consequence:

```
[FAIL] config.vector_db — VECTOR_DB is "PGVECTOR", which no provider matches:
       the selection is compared as a raw string, so this falls through to the
       default and the app will silently store vectors in LanceDB instead of
       PostgreSQL.
```

That is the finding stated as an outcome the operator can recognise. Before this
commit the same input produced `ext.permitted` failing over a `vector` extension
the instance would never have used — a true refusal for a misleading reason.

C3 and C4 are what make C1/C2 mean something: the check discriminates on
spelling, not on the presence of `pgvector` anywhere in the value.

## Ruling 2 — `ext.permitted` states which of the two claims it is making

| id | database state | detail |
|---|---|---|
| N1 | neither extension installed | `permission verified by creating and rolling back, which writes inside a transaction that is rolled back so nothing is left behind: pg_trgm, vector` |

untested one side by side, without conflating them. The nit from the previous

checked; they no longer do.

extname='vector'` on `qa3_74f` returns no rows.
