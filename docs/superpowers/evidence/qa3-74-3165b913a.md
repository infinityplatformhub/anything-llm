### `ext.permitted` is honest about what it did and did not test

The check probes only extensions that are **absent**, because
`CREATE EXTENSION IF NOT EXISTS` on an installed extension succeeds without
touching permissions. Measured with a role holding no `CREATE` right, against a
database where `pg_trgm` was installed and `vector` was not:

```
[FAIL] ext.permitted — Cannot create: vector (42501). already installed: pg_trgm;
       probed by creating and rolling back …: vector.
```

The two are reported as different facts. With both extensions installed the same
role gets `[PASS] ext.permitted — already installed: vector, pg_trgm.` — which is
correct: the deployment can use them, and no claim is made about a privilege the
role does not have.

## Entrypoint

| id | what | result |
|---|---|---|
| E1 | `entrypoint doctor` against a stub tree | runs the doctor, **does not boot the server**, exit 0 |
| E1b | `STORAGE_DIR` unset + `doctor` | the 14-line banner does not precede the checklist — the `case` really is first |
| E2 | doctor exits 1 | entrypoint exits **1** — `exec` is not decorative; without it `wait -n; exit $?` discards the code |
| E3 | serve path, doctor fails | `ENSURE RAN` → `DOCTOR FAILED` → **no `PRISMA RAN`, no `SERVER BOOTED`** |
| E4 | serve path, doctor passes (control) | `ENSURE RAN` → `DOCTOR PASSED` → `prisma generate` → `prisma migrate deploy` → `SERVER BOOTED`, in that order |
| E5 | `entrypoint bogus` | `unknown command: bogus (expected 'doctor' or 'serve')`, exit **64** |

E3 is the ordering §7.13 exists for: a `CREATE EXTENSION` that fails inside
`migrate deploy` leaves the database in a failed-migration state that blocks every
later migration, so the doctor has to run first. E4 is what makes E3 mean
something — without it, a chain that never runs anything would also pass.

"probed" when the extension is present, since that sentence is the whole reason
the branch exists.

## Documentation

`docker/HOW_TO_USE_DOCKER.md` states the uid trap in the operator's language,
names `env.writable` as the check that reports it, gives the
`UID=$(id -u) GID=$(id -g)` invocation, explains why `--no-deps` matters for an
external PostgreSQL, and says outright that the extension check writes and rolls
back. That last one is the disclosure ruling 2c asks for, and it is in the file
an operator reads rather than only in a code comment.

as belt-and-braces rather than as the fix — correct, since `postgres:16` already
sets `LANG=en_US.utf8` and the bundled path is not affected today.
