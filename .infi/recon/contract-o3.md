# O3 — backup / restore: evidence contract

Skills: `infi-dev` (evidence contract), `brainstorming` (open items framed as
questions rather than resolved by assumption).

Docs only. No code in this SHA. Derived from `.infi/recon/recon-o3.md`
(`5f8c1a8e2`) plus measurements taken while writing this file — every number
below was run, not reasoned about.

**Risk tier: `auth`.** Not self-classified — stated here for the PMO to confirm
at contract time. It touches secrets (`SIG_KEY`, `credential_store`), schema
(restore writes every table), and authorization state (`policy_versions`,
`principal_role_grants`). Any one of those alone is the `auth` tier.

## 1. The O3 ruling — sequence-jump on restore

**Ruling: a restore must replay identity sequences, and a bundle that carries
rows without them is incomplete rather than merely inconvenient.**

Why it is a ruling and not a preference — measured, not argued:

```
$ createdb o3probe
$ CREATE TABLE t (id serial PRIMARY KEY, v text);
$ INSERT INTO t (v) VALUES ('a'),('b'),('c');
$ SELECT last_value FROM t_id_seq;          → 3

# restore the ROWS with explicit ids, the way a JSON/row-level bundle does:
$ INSERT INTO t (id, v) VALUES (1,'a'),(2,'b'),(3,'c');
$ SELECT last_value, is_called FROM t_id_seq;   → 1 | f

$ INSERT INTO t (v) VALUES ('d') RETURNING id;
ERROR:  duplicate key value violates unique constraint "t_pkey"
DETAIL:  Key (id)=(1) already exists.
```

The restored database **looks correct**: three rows, right ids, every query
answers the way it did before. It fails on the first *write*. That is the shape
worth naming — a restore that passes every read-only smoke test and breaks when
the first user creates something.

`pg_dump` does not have this problem; it emits
`SELECT pg_catalog.setval('public.t_id_seq', 3, true);`. So the ruling is really
a constraint on **bundle format**: if O3 dumps rows itself (to redact, to
re-encrypt, to filter by org) it has left `pg_dump`'s guarantees behind and owns
this explicitly.

**Scope, measured on `server/prisma/schema.prisma`:**

- 57 models
- **49** use `@default(autoincrement())`
- 8 do not: `identity_login_state`, `identity_providers`, `jobs`,
  `job_schedules`, `event_outbox`, `role_permissions`, `group_members`,
  `document_visibility`

**The 48-vs-49 discrepancy is resolved** (TL-2 pre-read, `f0613ec3e`). It was
`directory_sync_checkpoints`, added by migration
`20260902130000_directory_sync_checkpoint` — my probe database was one migration
behind, so the table was simply absent. Nothing is declared-but-unmaterialised;
the real count is 49.

But resolving it surfaced the more useful fact. That table is the only one
declared as **IDENTITY** rather than `serial`:

```sql
-- 20260902130000_directory_sync_checkpoint/migration.sql
CREATE TABLE "directory_sync_checkpoints" (
  -- IDENTITY, not `serial`: the sequence belongs to the column's lifecycle rather
  -- than being a separate object with its own ownership and GRANTs to keep in step.
```

IDENTITY still has a sequence, and it jumps identically — measured:

```
CREATE TABLE i (id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY);
INSERT INTO i (id) VALUES (1),(2),(3);      -- row-level restore
SELECT last_value, is_called FROM i_id_seq; -> 1 | f
INSERT INTO i DEFAULT VALUES;
ERROR:  duplicate key value violates unique constraint "i_pkey"
```

**The trap is in how you enumerate.** A scan keyed on `column_default LIKE
'nextval%'` — the obvious predicate, since that is what `serial` produces —
finds the `serial` column and **misses the IDENTITY one**, because IDENTITY has
no `column_default` at all:

```
table | is_identity | column_default
  i   |    YES      | -                              <- invisible to a default-scan
  s   |    NO       | nextval('s_id_seq'::regclass)
```

Measured: that predicate returns **1** where the answer is 2. Both appear in
`pg_sequences`. So the enumeration must be
`is_identity = 'YES' OR column_default LIKE 'nextval%'`, and a test built on the
narrower predicate would report full coverage while never touching the one table
whose shape differs — the §7.17 failure class, arriving through the scan rather
than through the assertion.

Collision is not limited to primary keys. **37** `@unique` / `@@unique`
constraints exist, and four models key on strings rather than integers
(`schema.prisma:477` `@default(uuid())`, and three with caller-supplied
`String @id` at `:666`, `:691`, `:717`). Those do not jump — they collide only
if the bundle and the live database were both written to. Different failure,
same table.

## 2. OPEN — `SIG_KEY` handling (user decides; do not resolve by default)

The recon established there is no middle position. Both options are real; each
buys something and costs something. **This is left open deliberately** — it is a
key-management decision, not an engineering detail, and picking one silently
would be exactly the "structural ruling from a summary alone" the dispatch rules
forbid.

### Option A — out-of-band operator input
`SIG_KEY` never enters the bundle. The operator supplies it at restore.

- **Buys:** the bundle is not a credential store. It can be copied to a laptop,
  attached to a ticket, or handed to a vendor without becoming an incident.
- **Costs:** a restore is now a two-party operation. An operator who lost the
  key has an unrecoverable bundle — and since #48 made the `credential_store`
  row the only copy, "unrecoverable" means every provider credential is gone,
  not unset. Disaster recovery gets a human dependency at its worst moment.
- **Failure mode if the user picks this and we build it badly:** a restore that
  proceeds without the key and leaves the instance quietly unconfigured. RF-3
  exists to make that impossible.

### Option B — stored in the bundle, encrypted under a restore passphrase
The key travels, wrapped under a passphrase the operator types.

- **Buys:** one artifact, one input. Recovery works from the bundle alone.
- **Costs:** the bundle's security is now the passphrase's security. It moves
  the problem rather than removing it, and moves it toward the end of the range
  where humans pick weak values. It also makes every stored copy of the bundle a
  target with a known, uniform structure.
- **Requires, if chosen:** an actual KDF (argon2id or scrypt with measured
  parameters), not a hash; a passphrase strength floor; and a decision about
  what happens when the passphrase is wrong — which must be "refuse", never
  "restore what we can".

**Not a recommendation, a constraint on either choice:** whichever is picked,
the failure must be loud. The two options fail differently but both fail
silently if built carelessly, and a silent failure here is discovered weeks
later when someone tries to use a provider.

## 3. Evidence contract

Each RF is stated as: what is asserted, and **how it is proved RED first**. An RF
that cannot be made to fail is not evidence — it is decoration, and §7.17 has
this failure class recorded three times already.

### RF-9 — sequence replay (the ruling above)

```
Assert:  after restore, for every table with an identity column, the next
         INSERT succeeds and does not collide.
RED:     restore a bundle with sequences stripped; the first INSERT into any
         such table errors with a duplicate-key violation.
```

**N is derived from the database, never hard-coded.** The test enumerates:

```sql
SELECT table_name, column_name FROM information_schema.columns
 WHERE table_schema = 'public'
   AND (is_identity = 'YES' OR column_default LIKE 'nextval%');
```

and then asserts **`enumerated == tested == N`**. All three, because each catches
a different way of passing while proving nothing: `enumerated == tested` alone
passes when the query returns zero rows; `tested == N` alone passes when the
enumeration silently narrowed. A constant may appear **only as a floor**
(`expect(N).toBeGreaterThan(40)`), which fails loudly if the enumeration breaks
and does not need editing every time a migration adds a table.

The fixture must cover **both shapes** — one `serial` column and one IDENTITY
column — for the reason measured above: the narrow predicate finds the first and
misses the second, and a suite containing only `serial` tables would report full
coverage of a scan that cannot see IDENTITY at all.

### RF-10 — refuse a bundle newer than the code

```
Assert:  a bundle whose migration set is not satisfied by the running binary is
         REFUSED, before any write.
RED:     take a bundle carrying a migration the binary does not have; without
         the check it restores partially and leaves tables the code cannot read.
```

**The bundle stores the whole `_prisma_migrations` table, and the comparison is
between sets — not between latest names.** Comparing "the newest migration
name" is wrong in a way that is easy to miss: migration directories are
timestamp-prefixed, so a name comparison quietly becomes a *date* comparison,
and two branches that both merged around the same time can produce a bundle
whose newest name sorts older than the code's while still containing a migration
the code has never applied. Set difference answers the real question — *which
migrations does the bundle have that I do not?* — and it also answers the
reverse, which is a different and recoverable case (`migrate deploy` fixes it;
the forward case has no down migration and can only be refused).

The refusal message must name the specific migrations in the difference, not
just the two version strings. An operator told "bundle is newer" has to go
digging; one told which migration is missing knows immediately whether it
matters.

### RF-11 — partial-restore atomicity

```
Assert:  a restore that fails midway leaves the target in its PRE-RESTORE
         state, not a mixture.
RED:     inject a failure after N tables (a constraint violation on table N+1
         will do); without atomicity the database holds restored rows for 1..N
         and original rows for N+1.., with the FK graph spanning both.
```

**The shape is fresh-then-swap**, not restore-in-place. A single transaction
covers PostgreSQL and covers nothing else: `STORAGE_DIR` is a filesystem and the
remote vector providers are network services, and no amount of SQL makes those
roll back. Restoring into a fresh location and swapping on success is the only
shape where all four stores fail together. If a future design departs from it,
the failure window it accepts must be written down rather than discovered.

**Additional assertion: no `policy.changed` event escapes a failed restore.**
A restore writes `principal_role_grants` and `policy_versions`; those writes
publish `policy.changed`, and the subscriber invalidates every cache listening.
A restore that rolls back after publishing has told every process in the
deployment that the policy moved — to a version that no longer exists. The
outbox must be part of the same atomic unit as the rows that justify it, and
this is asserted by counting outbox rows before and after a *failed* restore, not
by inspecting the code path.

### Inherited from the recon, restated for completeness

- **RF-1** round trip: same authorization *decisions*, asserted through the
  engine — equal row counts with a different `policy_version` is not success.
- **RF-2** no `SIG_KEY` or decrypted credential in the artifact (grep the
  produced bundle; must fail before the fix).
- **RF-3** restore without the key **refuses**, rather than booting
  unconfigured. Load-bearing under Option A.
- **RF-4** AAD: a row restored under a different `envKey`, or with a bumped
  `KEY_VERSION`, is refused by the auth tag
  (`credentialStore.js:119` binds both). Asserted as *refused*, distinctly from
  *decrypted wrongly* — the recon's point that a runbook checking exit codes
  cannot tell those apart.
- **RF-5** migration gap: an older dump restores only after
  `migrate deploy`, and the failure before it is legible.
- **RF-6** cross-store skew, **both directions**, vector-orphans refused rather
  than served.
- **RF-7** revoked-grant regression — *write this one first*. Revoke, restore a
  backup predating the revocation, assert the grant is not live.
- **RF-8** the same restore path exercised for LanceDB (file-backed, inside
  `STORAGE_DIR`) and one remote provider. They cannot share an assertion that
  holds for only one.

### RF-12 — a restore that moves `policy_versions` backwards must not serve stale entries

This is open question 1 from the recon, promoted to an RF now that TL-2 has
confirmed the mechanism.

```
Assert:  after restoring a backup whose policy_versions head is LOWER than the
         cache's stamped version, no cached filter is served.
RED:     mutate the freshness check to `entry.policyVersion <= head` and confirm
         the test goes red. If it stays green the test is not reaching the
         comparison.
```

The mechanism, read at `utils/authorization/cache.js:93-99`:

```js
const head = String(await currentPolicyVersion(input.db ?? this.db));
const fresh =
  entry &&
  entry.policyVersion === head &&
  Date.now() - entry.storedAt < this.ttlMs;
```

The comparison is `===`, and that strictness is what makes a backwards move
safe: an entry stamped at version 40 does not match a restored head of 12, so it
is rebuilt. A `<=` — which reads as the natural "not older than", and is exactly
what a well-meaning refactor would write — would serve the version-40 entry
against the version-12 database: a cached grant surviving a restore that was
supposed to remove it. Hence the named mutant. The RF exists to pin `===`
against that specific rewrite, not to test caching in general.

`currentPolicyVersion` (`policyRepository.js:512-518`) reads `policy_versions`
ordered by version descending on **every** `get`, so the head is always the
restored database's head rather than a remembered value. That per-call read is
deliberate and is what makes this work; see §5.

## 4. Contract command

Not runnable yet — there is no O3 code. Recorded now so it is fixed before
implementation rather than chosen afterwards to match what got built.

```
cmd:    cd server && npx jest __tests__/backup --runInBand
expect: Tests:  <N> passed, <N> total     with N >= 13
        and the sequence test reporting the table count it examined
```

The `N >= 13` floor and the count-reporting requirement are both there for the
same reason: `Tests: 0 total` and "all passed" render identically, and a
sequence test that silently examined one table passes just as green as one that
examined 49.
