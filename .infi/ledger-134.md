## Correction: TL-1's F1 premise is false, measured

The pre-read (R4/F1) states that passing a `tx` to `addGroupMember` "silently converts
batch-per-entity into batch-per-run and collapses every membership change into one
version bump", with the witness: "two membership changes must produce two
policy_versions rows. Mutant: pass a tx — one row."

**Measured on `s4b2_mig_probe`, real repository, two membership changes:**

```
TX-WRAPPED  two changes  -> policy_versions delta: 2
PER-ENTITY  two changes  -> policy_versions delta: 2
TX-WRAPPED  two removals -> event_outbox   delta: 2
```

`inTransaction` (policyRepository.js:23-24) makes a repository call run INLINE when
handed a tx — that part is correct — but `bumpVersion` is called once per
`addGroupMember` invocation either way, so the row count is identical. The proposed
mutant (M2/M3, both shapes: per-call `$transaction`, and one transaction wrapping the
whole loop) **survives the entire suite**, because there is nothing to observe.

What passing a `tx` actually changes is ROLLBACK SCOPE and lock duration: one conflicting
row discards every membership change in the run, and a 100-page org holds locks for the
whole apply. That is the real reason for the ruling, and it is not observable as a row
count — it needs a conflict fixture. Recorded rather than tested here: the fix
(pass `prisma`) is already in the SHA, and the pre-read's own witness would have been a
test that passes for a reason unrelated to what it names — the exact failure class
§7.17 exists for.

**Recorded as a SURVIVOR with its reachability: M2/M3 are unkillable as specified.**
