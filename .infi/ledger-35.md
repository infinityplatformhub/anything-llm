# Ledger — issue 35, PR-4d: the API-key scope ceiling

PR-4c made every key carry an enumerated list instead of `"*"`. The list a caller could ask for was still a preset chosen by which endpoint they hit, and nothing compared it to what the creator actually held. #27 recorded that as a ponytail because both mint sites are admin-gated — that entry is now deleted, not amended, because the condition it described no longer exists.

QA-2 confirmed the hole on main while this was in flight: an admin POSTing `["system.env.read"]` to `/admin/generate-api-key` was handed it and read the provider credentials through `/v1/system/env-dump`. The preset was never a ceiling; it was a default with nothing above it.

Ruling: **two checks, two error types.** `KeyMintForbiddenError` answers "may this principal mint a key at all" (`key.manage`), `ScopeCeilingError` answers "may it grant these scopes". Collapsing them would let a bug in the first hide behind a failure in the second — the seeded `member` role holds only `chat.send`, so a member's request fails either check, and an implementation that never asked about `key.manage` would still look correct. If wrong, the two errors are more code than one; the cost of merging them is a check that silently stops running.

Ruling: **the recon's `member` case could not test what it claimed.** The RED suite inherited from the earlier branch asserted that a member is refused for lacking `key.manage`, but `member:org` holds `chat.send` alone — which is not in `KNOWN_SCOPES` at all, so it can never be requested, and every member request also fails the scope ceiling. Added `content_moderator`, which holds `document.read`/`document.search` (real route scopes) and NOT `key.manage`: asking only for scopes it holds, it must still be refused, and only the authority check can explain that. Without this the suite would pass against a ceiling that never reads `key.manage`.

Ruling: **the brief's "manager" role does not exist.** Seeded roles are `super_admin`, `setup_admin`, `content_moderator`, `member` (org) and `owner`, `editor`, `viewer` (workspace). "manager" is a legacy `users.role` string, not a principal the engine knows. The case the brief wanted is `setup_admin` — it holds `key.manage` but not `system.env.read`, which is exactly the separation PR-4b(4) created. Reported to PMO rather than implemented as written.

Ruling: **a default narrows, an explicit request refuses** (PMO ruling 2). `trimToCeiling` is set only by the endpoints, and only when the caller named no scopes: an unmodified client posting `{name}` keeps working and receives `preset ∩ grants(creator)`. A caller who NAMED a scope gets a 400 that lists what they lack, because a silently smaller key is one they discover at the first 403 from a route, with nothing saying why. If wrong, a client that sends a scope list must handle a 400 it did not have to handle before — which is the correct conversation to force.

Ruling: **trimmed-to-empty is refused, not minted.** A key with an empty scope list authenticates and can do nothing: it looks like a working credential and behaves like a revoked one. The refusal names `key.manage` when that is what is missing, so the operator is not told to go collect scopes when the real problem is authority.

Ruling: **`keyGrantPrincipal` is reused, not reimplemented** (PMO ruling 4). It already carries the rule that a null creator resolves to the single-user service principal ONLY when `isConfirmedSingleUser` agrees (QA-2 FINDING-1); a second resolution here would be a second place for that gate to be forgotten. It needed exporting from `actorResolver` — the export comment says why, next to the one `isConfirmedSingleUser` carries for the same reason.

Ruling: **membership, not a grant, gates a bound key.** A creator binding a key to a workspace must be a member of it. An org-wide reader is not thereby a member, and the binding is what the engine enforces at request time (`outside_key_binding`), so the mint check has to ask the same question the request path asks. Service principals are allowed through: they have no membership rows, and a single-user operator administers every workspace.

Ruling: **`apiKeyScopes.test.js` stubs the ceiling rather than mocking the policy store.** That suite's subject is the SHAPE validation that runs first — wildcard, empty list, typo — and it mocks prisma down to `api_keys.create`. Adding role tables to its mock would make it a second, worse copy of `keyScopeCeiling.test.js`; stubbing `applyScopeCeiling` to allow keeps the two concerns separable, and the real engine against real seeded grants is driven in one place.

Ruling: **the HTTP suite's end-to-end case was rewritten after its RED proof passed.** The first version minted a default-scoped key and asserted `/v1/system/env-dump` returned 403 — which was already true before the ceiling, because the preset never contained `system.env.read`. It passed in RED, which is the tell. Rewritten to walk QA-2's actual path (ask explicitly, be refused at the mint) with a `super_admin` positive control that DOES read env-dump, so a 403 cannot come from a broken route or an empty scope table. RED now fails 4 of 7; the 3 that stay green are the positive controls, deliberately.

Ruling: **`chatReadOthers.test.js` seeds its two API keys directly instead of through `ApiKey.create`.** Its fixture mints a key whose creator is `plainAdmin` — a legacy admin holding only `member` — because the pair's entire claim is that two keys with IDENTICAL scopes differ only in whose grants stand behind them. Under the ceiling that creator now lacks `key.manage`, so the mint refuses and the suite never reaches the question it asks. Seeding the rows keeps the subject the GRANT half at REQUEST time; mint-time authority is `keyScopeCeiling.test.js`'s subject and is not weakened by this. If wrong, a fixture bypasses a check that production callers cannot — which is why the comment names the split explicitly.

Note on the full-suite run: 6 tests fail on this branch, and the same 6 fail on **clean main (3060171c) with this branch absent** — `engine.test.js` ×3, `grantManagement.test.js` ×1, `routeWiring.test.js` ×2, all in T-7 (#31) territory. Verified by resetting a separate worktree to main and running the whole suite there. Not introduced here; reported rather than absorbed.
