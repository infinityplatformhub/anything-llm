# Ledger — issue 48, an explicit path to clear a stored credential

`persistCredential` has a delete branch for an empty value, and `credentialStore.js:50` says "delete the row to clear it". Neither runs. I measured it: of the 91 `secret: true` keys, **49 carry a validator that rejects `""`** before `updateENV` reaches the branch — `OpenAiKey`, `AnthropicApiKey`, `GeminiLLMApiKey` among them. So for the credentials most worth revoking, there was no way to revoke one.

Ruling: **`force` is not the missing answer, and a test says so.** `executeValidationChecks` passes `force` to every validator, which makes "just send force" look like an existing escape hatch. It is not: those validators never read the flag, and `check("", true)` still returns `"Value cannot be empty"`. The suite asserts this directly rather than in a comment, so if a future change makes empty values acceptable, the test fails and someone re-reads whether this route is still needed.

Ruling: **a separate route, not a sentinel value** (PMO). A magic value in the update payload would sit on the path shared by all 213 settings, one typo away from clearing a credential nobody meant to touch. `DELETE /system/credential/:envKey` is one route, one meaning, and does not touch the update path at all.

Ruling: **both halves, or it is not a revocation.** Deleting only the row leaves `process.env` serving the credential until the next restart — the operator is told it is gone while it still works, which is a false belief in the unsafe direction. Unsetting only the variable leaves the row, and `loadStoredCredentials()` restores it on the next boot. A test drives `loadStoredCredentials()` after the clear and asserts the value does not come back, because "gone until reboot" was the actual pre-existing behaviour.

Ruling: **the row is deleted first, and a failed delete clears nothing.** If the store delete fails, the live value stays too. A half-cleared credential that reappears on the next boot is worse than one that never left, and the caller is told the clear did not happen rather than being given a 200 that means "partly".

Ruling: **only a `secret: true` envKey is accepted; anything else is 400.** Without this the route unsets any process environment variable from an HTTP request. The suite names `STORAGE_DIR`, `JWT_SECRET`, `DATABASE_URL` and `SIG_KEY` explicitly and asserts each is both refused and still set afterwards — a 400 alone would not prove the variable survived.

Ruling: **clearing a credential that is not stored is a 400, not a 200.** A success there tells an operator a credential was revoked when no row existed, which reads as "it is gone" whether or not it ever was.

Finding, fixed here: **the audit event's `envKey` was being dropped.** `utils/events/redaction.js` drops any key not on its allowlist and records only `_droppedKeyCount`, so the first version of the event stored `{"_droppedKeyCount":1}` — a row saying something was cleared without saying what. The allowlist is deliberately closed and adding to it is meant to be an explicit act, so this is that act: `envKey` is added with a comment recording why it is safe. Its value is a `KEY_MAPPING` envKey and the route refuses anything else, so it cannot carry caller-chosen free text — which is the specific risk the allowlist exists to stop. The test asserts the event contains the key name and does **not** contain the secret: an audit row holding the credential would outlive the credential it was written to retire.

## Round 4 — QA-1 BLOCKER-1 and Techlead review

Ruling: **`secret: true` is not the same question as "safe to unset".** QA-1 walked it end to end: `DELETE /system/credential/AUTH_TOKEN` returned 200, and with `AUTH_TOKEN` unset `validatedRequest.js:29-36` takes its passthrough branch — `!process.env.AUTH_TOKEN` skips session auth entirely — so an unauthenticated caller reached `POST /system/update-env`. The row is deleted, so boot does not restore it: the instance stays open permanently. `JWT_SECRET` is the same flag with a different blast radius (every live session invalid at once). Both carry `secret: true` for a real reason — they must not be written to `.env` in plaintext — and I read that flag as answering a question it does not answer. `INSTANCE_AUTH_KEYS` refuses them by name, before the credential-key check.

Ruling: **the denylist names five keys, three of which are not in KEY_MAPPING today.** `SIG_KEY`, `SIG_SALT` and `API_KEY_PEPPER` are already refused by the credential-key check because nothing maps them. They are listed anyway: SIG_KEY and SIG_SALT derive the credential store's own encryption, API_KEY_PEPPER validates every API key, and a denylist that only covers today's mapping is one PR away from being wrong. This makes the "denylist ⊆ allowlist" test PMO asked for false as literally stated, so it is written as two: every denylisted key matches `ENV_KEY_PATTERN` (a typo protects nothing and looks identical to a correct entry), and `AUTH_TOKEN`/`JWT_SECRET` really are in the allowlist — which is what proves the denylist is load-bearing rather than decorative.

Ruling: **a sweep, not a list, guards the general case.** One test parses the passthrough condition out of `validatedRequest.js`, extracts every `process.env.X` it names, and asserts no `secret: true` key outside the denylist appears there. A future credential key added to that condition fails here rather than in production.

Ruling: **the key name is validated for SHAPE before it is used, and the rejection does not echo it.** `^[A-Z0-9_]{1,64}$`, checked first. The name arrives on a URL path, so reflecting it into the response body is caller-controlled text; the message is the same string for every malformed key, so it also says nothing about which spellings get further.

Ruling: **`/request-token` answers 401, not 500, when `AUTH_TOKEN` is unset.** `bcrypt.hashSync(undefined, …)` throws, so a login attempt against an instance with no password returned 500 — an error shape that tells a caller something broke here, and which was not even true: nothing broke, there is no password to match. Same status and same `[003]` body as a wrong password.

Two defects in my own tests, both caught because the suite went red rather than by review:
- the denylist case deleted `process.env.JWT_SECRET` and did not restore it, so eight later tests in the same file died with `Cannot create JWT as JWT_SECRET is unset` — a fixture that takes the harness down is indistinguishable from the code being broken.
- it then wrote a canary into `process.env.SIG_KEY`, which derives the store's encryption key, making the row written a moment earlier undecryptable. The fixture now stores a row and asserts the live value is unchanged from whatever it was, rather than overwriting it.

RED with the denylist disabled fails 10 of 27, including all five denylist cases and `the instance stays authenticated after a refused clear`.

Residual (not fixed here, reported):
- The passthrough branch in `validatedRequest` is still reachable by other means — `update-password` with `usePassword: false` unsets `AUTH_TOKEN` through the supported path. #48 only stops the credential-clear route from being one of those means; the branch itself is #52/#58 territory.
- `clearStoredCredential` does not run `postUpdate`/`postSettled` hooks. No `secret: true` key defines one today (0 of 91), so nothing is skipped — but a key that gains one later would have it skipped silently on clear.
- A value already present in `.env` when dotenv loads wins over the store, so clearing a credential does not remove a value an operator put in the file by hand. Revoking a key means checking `.env` too.
