# Ledger — issue 41, bound API key reaches cross-tenant document storage

Fifteen /v1 routes carry a workspace slug and are bound by the scope middleware. Seven document routes carry no workspace at all, so `validApiKey` treats them as org-level questions and cannot refuse them — and nothing else did. A key issued for workspace A listed, read, moved and deleted workspace B's documents. QA-2 reproduced it on 4c32bce3.

Ruling: **strict join** (PMO). A bound key sees a document only when a `workspace_documents` row attaches it to that key's workspace. Documents on disk with no row — uploaded but never attached — stay invisible. The alternative considered was "own workspace plus orphans", which keeps upload→list working but makes the orphan set a shared channel: tenant A would read whatever tenant B had uploaded and not yet embedded. If wrong, a bound key cannot see a document until it is attached, which the write-side fix below makes automatic.

Ruling: **the write side ships in the same PR**. `attachTargets` attaches a bound key's upload to its bound workspace when the caller names no `addToWorkspaces`. Without it the strict join creates a window where a key uploads a document and is then told it does not exist. Unbound keys are untouched, and an explicit list from a bound key is already constrained by `validateWorkspaceSlugQuery`, so it passes through unchanged. Four routes, one helper: `upload`, `upload/:folderName`, `upload-link`, `raw-text`.

Ruling: **404, not 403, on `GET /v1/document/:docName`** (PMO amendment, §3.4). A document name is a user-chosen slug, so a 403 would confirm that name exists somewhere in the deployment. The handler resolves FIRST and compares after — never short-circuits on the binding — so the two paths do the same work and return the same body. A test asserts the two responses are byte-identical, because a status code that differs by a millisecond of work is still an oracle.

Ruling: **folder routes and generated-files refuse a bound key outright.** Folders have no owner in the database, and generated files land flat in `$STORAGE_DIR/generated-files` with no row anywhere — I checked `schema.prisma` for `generated_file|generatedFile|agent_file` and found nothing, and `saveGeneratedFile()` writes the file and returns metadata to the WebSocket without inserting. There is no owner to compare a binding against, so "compare the row" could not be implemented as first ruled; PMO's amended answer is refusal, the same class as the folder routes. A per-file owner table is a separate issue.

Ruling: **`findDocumentInDocuments` now returns `docpath`** and the handler strips it before responding. The finder walks storage and previously returned only a name, which is not the join key. One caller, so no contract broke — and a test asserts the field never reaches the response, because handing a bound key the folder layout is the thing it is being kept out of.

Ruling: **the join fails closed.** An unreadable `workspace_documents` returns an empty allow-set, not "no restriction". Falling through to the full listing would turn a database hiccup into the exact leak this issue is about.

Correction to my own recon report: I told PMO that `boundKeyWorkspaceScope` "does not exist". It exists — as `__tests__/endpoints/boundKeyWorkspaceScope.test.js`. I had grepped `server/utils` and `server/endpoints` and concluded from an absence in two directories. The substance stands (it is not a shared guard; the narrowing is inline at `endpoints/api/workspace/index.js:154` and `:82`) and that is what made the citation misleading — a comment pointing at a test named after a property reads as though a check enforces it. The replacement comment says which lines actually narrow and that anything added to the carve-out must bring its own.

Correction to the brief: PMO asked for a test that **removing the creator from the workspace** refuses a bound key immediately. It does not, and should not. These routes carry no workspace, so the engine evaluates them against the org (`workspace_id: null`), where an org-wide grant answers regardless of membership. Membership narrows workspace-bearing resources. Written instead as: revoking the creator's ROLE refuses immediately (which is the request-time-vs-mint-time claim the check was for), plus a second test stating plainly that membership is NOT what authorizes these routes — it is the surprising half, and a comment would have been lost.

Verification: 18/18 on the suite; RED with the helper neutered fails 10 of 18 and the 8 that stay green are every positive control, deliberately. Full suite on a freshly created database: 1235/1235, 118/118 suites.

## Review round 2 (Techlead pre-check + QA-1)

Ruling: **`findDocumentInDocuments` reads the stored name back off disk** rather than using the requested one. Techlead's blocker was right that the docpath must not come from the request; the mechanism they named was not the one that bites. I checked each case: for `./x.json`, `a//b`, and surrounding whitespace, `normalizePath` either produces exactly the on-disk name (nothing differs) or produces a name `existsSync` cannot find (the finder skips the folder and answers 404 as it always did). Neither reaches the docpath comparison. **Unicode does**: macOS stores NFD while a request commonly carries NFC, `existsSync` resolves either, so the document IS found — and a docpath built from the request is then not `===` the one written at ingest, and the key is told 404 about its own file. The test is written on that case, and RED with `storedNameFor` removed fails exactly one test: the NFC-vs-NFD read. My first attempt at this test used `./` and whitespace spellings and **passed without the fix** — a RED proof that comes back green is the only reason I found the difference.

Ruling: **a failed attach is a 500, not a silent 200.** The orphan is left on disk (deleting a file the caller may still want is worse), but `success: false` and an error naming "uploaded but not attached" go back, because under the strict join that document is invisible to the very key that created it and cannot be deleted through these routes either. A 200 would describe a working upload that produced something unreachable.

Ruling: **the write half is tested through `raw-text`,** the one upload path needing no multipart body, with the collector stubbed to write a real file under `STORAGE_DIR` so the upload and the listing meet on disk as they do in production. The other three take multipart or reach the network; they are covered structurally — the suite asserts all four call sites go through `attachTargets` and that the old `if (!!addToWorkspaces)` shape is gone from the file, which is what left the write-side hole.

Ruling: **QA-1's cross-tenant case is tested on all four routes.** `attachTargets` returns an explicitly-named list untouched, relying on `validateWorkspaceSlugQuery` having refused anything outside the binding. That reliance is exactly what needed a test: reorder the middleware off any route and attachTargets would attach across tenants with nothing else noticing. A bound key of A naming B's slug is refused on all four, a same-workspace slug is the positive control, and a final case asserts no row was written to B by any of the refused calls — the status says refused, the row count says nothing happened.

Note: the write-half tests exposed a gap in my own harness, not in the code — the vector-driver mock lacked `addDocumentToNamespace`, so attaching threw and the route answered 500 with an empty body. Stubbed the driver rather than running a real embedder: what these tests assert is the `workspace_documents` row and the listing.

Verification: 33/33 on the suite. Full suite on a freshly created database: 1250/1250, 118/118 suites.
