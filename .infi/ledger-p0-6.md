# P0-6 ledger

Ruling: Implement queue directly on Prisma/Postgres rather than add pg-boss — binding contract needs custom immutable ActorRef, leasing, and dead-letter semantics; existing Prisma and pg dependencies suffice — if wrong, scheduler maintenance costs more than pg-boss adoption.
Ruling: Keep P0-6 Prisma models in delimited final schema block and separate migration — P0-2 owns provider and base migration — if wrong, rebase may need manual migration consolidation.
Ruling: Develop and unit-test drivers through injected Prisma-compatible stores, with Postgres DDL supplied separately — parallel P0-2 branch owns runnable Postgres test substrate — if wrong, SQL-specific lease behavior needs follow-up integration fixes after rebase.
Ruling: Preserve EventLogs.logEvent as compatibility delegate but migrate production call-sites to emitAuditEvent — external plugins may still import model API — if wrong, compatibility surface hides a forbidden direct call.
Ruling: Audit delivery runs immediately after non-transactional publish to preserve existing await semantics; transactional publishers rely on outbox pump — if wrong, transactional audit visibility is delayed until worker tick.
Ruling: Retention purge handler logs and returns zero only — S6 owns authorization and deletion policy — if wrong, placeholder may imply more governance coverage than exists.
Ruling: Use transaction-scoped Postgres advisory lock in scheduler pump plus occurrence idempotency key — singleton behavior survives multiple server processes without session-lock pool leakage — if wrong, advisory lock key collision may serialize unrelated future scheduler.
Ruling: Persist subscriber version quarantine and emit event.delivery_failed with explicit recursion guard — unknown schema must not be guessed and failure observability must not create infinite events — if wrong, wildcard subscribers need per-type version maps instead of global supported versions.
Ruling: Start outbox recovery immediately at boot and poll every second; start scheduler immediately and poll each minute — committed events and schedules survive restart without another trigger — if wrong, polling load requires LISTEN/NOTIFY optimization.
Ruling: Boot one durable JobRuntime that registers schedules, enqueues telemetry flush, polls claimed jobs, and owns shutdownable worker/scheduler timers — contract requires runtime recovery rather than library-only code — if wrong, process lifecycle needs integration into broader BackgroundService ownership.
Ruling: Treat jobs as mutating unless payload explicitly declares mutating:false — impersonated provenance must fail closed at enqueue and execution — if wrong, read-only job authors must add one explicit field.
Ruling: Query outbox only where subscriber delivery is absent or retry is due, with fixed batch limit and indexed delivery state — avoids full historical scans — if wrong, high subscriber cardinality may require raw SQL SKIP LOCKED claims.
Ruling: @breejs/later was already installed and is reused for cron parsing rather than adding a scheduler dependency — fewer runtime dependencies and existing cron semantics stay consistent — if wrong, DST edge behavior requires Temporal or a timezone-native cron library.
Ruling: telemetry.flush queued handler calls existing Telemetry.flush API even though current de-brand adapter is a no-op — queue migration is real while telemetry remains intentionally disabled — if wrong, future telemetry adapter inherits durable flush without handler changes.
Ruling: heartbeat lease loss is logged but cannot cooperatively abort arbitrary handlers yet — handler cancellation needs AbortSignal contract extension — if wrong, long side effects may continue until complete rejects after lease loss.
Ruling: Scheduler performs at most one catch-up occurrence after downtime, then computes nextRunAt from max(overdue runAt, now) — preserves one governance run without replay storms or skipping directly with no work — if wrong, compliance policy may require every missed interval and needs an explicit capped backlog table.
Ruling: Advisory-lock query is unconditional because singleton correctness depends on it — database/fake incompatibility must fail loudly rather than silently disable locking — if wrong, non-Postgres drivers require a separate scheduler implementation.
