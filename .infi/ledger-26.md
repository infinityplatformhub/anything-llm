# Ledger — issue 26, PR-4b(1) workspace + thread scopes

Ruling: renamed `PR4A_ROUTE_SCOPES` → `ROUTE_SCOPES` in a separate commit before touching any route — the table stops being PR-4a's the moment a second PR appends to it, and four are about to. Grep confirmed nothing outside `scopes.js` imported the old name (only its own test), so no alias was kept. If wrong, a later PR written against the old name fails at require time, loudly.

Ruling: `POST /v1/workspace/:slug/update-pin` gets **`document.pin`**, not the recon's `workspace.embeddings.manage` — `document.pin` already exists in the seeded vocabulary as a document action, and pinning is a per-document flag, not a change to what the workspace embeds. Folding it into the embeddings scope would mean a key that may only pin can also attach and detach documents wholesale. If wrong, an integration that pins documents needs a second scope granted alongside the one it has.

Ruling: `POST /v1/workspace/:slug/vector-search` gets **`document.search`**, not the recon's invented `workspace.search` — `document.search` is already in the vocabulary and is exactly what the route does (T-3's `documentFilter` treats `document.read`/`document.search` as the two filterable actions). Adding `workspace.search` would create a second name for the same capability, which is what R3 forbids. If wrong, the scope reads as narrower than the route (it searches within one workspace), but the vocabulary stays single-namespace.

Ruling: added five new actions (`workspace.create`, `workspace.embeddings.manage`, `thread.create`, `thread.write`, `thread.delete`) rather than reusing `workspace.write` for all of them — creating a workspace is not editing one, and a key scoped to edit the workspaces it was given must not be able to mint new ones. Threads are a distinct resource with their own lifecycle. If wrong, the scope list is five entries longer than it strictly had to be.

Ruling: shipped a migration (`20260902040000_pr4b_workspace_thread_scopes`) rather than only editing the seed file — the step-7a `CROSS JOIN` granted `super_admin` every permission that existed **at that moment**, so rows inserted by a later seed run are not covered by it. Without the explicit re-grant, `super_admin` silently lacks the five new actions on any database that already ran T-1. Verified against the T-1 migration's own grant blocks. If wrong, the migration is a no-op on a fresh database, which is harmless.

Ruling: granted the four workspace-level new actions to `owner` and `editor` but kept `workspace.create` org-level (`super_admin` only) — a workspace role acts inside its workspace; minting new workspaces is not inside it. If wrong, a workspace owner has to ask an org admin to create a workspace, which is the intended shape.

Ruling: bound all 15 slug-carrying routes with `{ workspaceSlugParam: "slug" }` and left only `POST /v1/workspace/new` and `GET /v1/workspaces` unbound — those two have no workspace in the path to bind against. `GET /v1/workspaces` therefore still lists every workspace to any key holding `workspace.read`; narrowing that listing is a handler change, not a middleware change, and belongs with T-4a route wiring. Recorded here so the reviewer does not read the missing binding as an oversight.

## PR-4b(2) document (branch `approof/pr4b-document`, base `dcc945d5`)

Ruling: document routes carry **no workspace binding**, as the recon directed — documents live in a global store and workspace attachment happens after upload, so there is no workspace in the path to bind against. Per-actor document scoping is T-3's `documentFilter`, which is merged. Stated in the table's comment so a reviewer does not read the absence as an oversight. If wrong, a workspace-scoped key can call document routes for documents outside its workspace until T-5 wires the filter into those handlers.

Ruling: `accepted-file-types` and `metadata-schema` get **`system.read`**, not a document scope — both return static capability metadata with no tenant data in them. A read-only monitoring key should be able to ask what the server accepts without thereby being able to read documents. If wrong, an integration that only touches documents needs `system.read` granted alongside.

Ruling: added **`document.folder.manage`** rather than reusing `document.write` for create-folder / remove-folder / move-files — a folder operation rearranges what other keys can reach by path; `document.write` covers a document's contents and `document.delete` covers one document, neither covers the container. Granted to `owner`/`editor` at workspace scope (they already create and delete documents there) and to `super_admin`; `viewer` stays read-only. If wrong, the scope list is one entry longer than it had to be.

Ruling: `generated-files/:filename` gets **`document.read`**, not `document.export` — the route serves a single file the agent produced by its parsed name, which is an ordinary read. `document.export`/`document.bulk_export` are the exfiltration paths T-2's review separated, and folding a per-file fetch into them would make the export scope required for normal use, which defeats the separation. If wrong, a per-file download is grantable without the export scope.

Ruling: migration slot **041000** per PMO's slot ruling (040000 taken by 4b-1, 4b-3/4 take 042000/043000, PR-4c moves to 045000).

## PR-4b(3) embed + browser extension (branch `approof/pr4b-embed-extension`, base `54db4028`)

Ruling: took PMO's **option (a)** — the browser extension's grant is fixed in code (`EXTENSION_SCOPES`) and its five routes are deliberately absent from `ROUTE_SCOPES`. One table holding scopes for two credential types cannot answer "which scope applies to which kind of key" during an audit, and the extension is a single-purpose client whose grant is not issued per key. If wrong, adding a sixth extension route means editing code rather than a table.

Ruling: reused the **already-seeded `browser-extension.read` / `.write`** rather than adding the `extension.*` names the recon proposed — grep found both actions already in the T-1 vocabulary. Adding `extension.read` alongside `browser-extension.read` would be a second name for one capability, which R3 forbids; the recon's table was written without checking the seed. Caught before the migration was written, so no slot was wasted. If wrong, the scope strings are longer than they need to be.

Ruling: `validBrowserExtensionApiKey` stops writing **`scopes: ["*"]`** into `apiKeyContext` and stops honouring `"*"` in its own check. The wildcard was not only a middleware bypass: `actorResolver` reads `apiKeyContext.scopes` verbatim, so every extension request was producing a service Actor holding every scope in the system, which the T-2 engine would then evaluate against. Removing it is what makes the fixed grant real rather than cosmetic. If wrong, an extension route needing a scope outside the four in `EXTENSION_SCOPES` returns 403 until the set is widened deliberately.

Ruling: added **`embed.chat.read`** separate from `embed.read` — embed chat transcripts are what the public typed into a widget, not the operator's own chats. A key that may read embed configurations must not thereby read visitor conversations. `embed.create` is likewise separate from `embed.write` for the same reason `workspace.create` is. If wrong, two more scopes to grant for full embed administration.

Ruling: the sweep test now asserts the burn-down through **two independent mechanisms** and says so in a comment: the regex counts only `validApiKey(...)` (47 API-key routes), while two added tests assert the extension file carries no wildcard and that the middleware neither stores nor honours `"*"`. Narrowing the regex alone would have let the counter reach 11 while the extension still held a wildcard — the exact "counter reaches zero while every key still holds `*`" failure mode flagged during PR-4c review. RED-proven separately: reverting an embed route fails the counter, restoring the middleware's wildcard fails the middleware test, and reverting an extension route fails the extension-file test. If wrong, three assertions where one number would have read more simply.

Ruling: migration slot **042000** per PMO's slot ruling; it seeds only the two embed actions, since the browser-extension actions were already seeded by T-1's step-7a.
